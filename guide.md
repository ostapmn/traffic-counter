# 1. Базова термінологія

## Кадр, піксель, канал

**Кадр** (frame) — одне зображення з відео. Для комп'ютера це тривимірний
масив чисел: `висота × ширина × канали`.

**Піксель** — одна точка зображення. У кольоровому зображенні описується трьома
числами — інтенсивностями червоного, зеленого й синього, кожне від 0 до 255
(тобто один байт).

**Канал** — одна «площина» зображення. Кольоровий кадр має 3 канали.

Приклад: кадр 1280×720 у кольорі — це масив форми `(720, 1280, 3)`, тобто
720 × 1280 × 3 = 2 764 800 чисел. При 30 кадрах/с це 83 МБ/с сирих даних —
саме тому відео завжди стискають.

**BGR vs RGB.** OpenCV (бібліотека, якою ми читаємо відео) історично тримає
канали у порядку **B**lue, **G**reen, **R**ed, а не RGB. Це джерело класичної
помилки: якщо подати BGR-кадр у мережу, навчену на RGB, кольори інвертуються й
точність падає. У нас це видно в коді:

```python
# 🔵 довідкова реалізація, повертається на кроці 27
mat_in = ncnn.Mat.from_pixels(
    canvas, ncnn.Mat.PixelType.PIXEL_BGR2RGB,  # ← явна конверсія
    input_size, input_size,
)
```

## Тензор

**Тензор** — узагальнення масиву на будь-яку кількість вимірів. Скаляр — тензор
0-го порядку, вектор — 1-го, матриця — 2-го, кадр — 3-го. Нейромережі
працюють із тензорами, і «форма тензора» (shape) — це кортеж розмірів.

Нотація: тензор форми `(1, 84, 2100)` має 1 × 84 × 2100 = 176 400 чисел.
Перший вимір зазвичай **batch** — скільки зображень обробляємо одночасно.
У нас завжди 1, бо обробляємо потік кадр за кадром.

## Згортка і карта ознак

**Згортка** (convolution) — операція, яка «проводить» маленьке віконце (ядро,
наприклад 3×3) по всьому зображенню, у кожній позиції множить значення під
віконцем на ваги ядра й сумує. Результат — нове зображення, яке підсвічує те, на
що ядро «налаштоване»: краї, кути, текстури.

Проста ілюстрація. Ядро для пошуку вертикальних краів:

```
     -1  0  +1
K =  -1  0  +1
     -1  0  +1
```

На рівномірній ділянці сума дорівнює нулю (ліве й праве компенсуються). На
межі «темне-світле» вона велика. Так мережа «бачить» контури.

**Карта ознак** (feature map) — вихід згортки, тензор форми
`(канали, висота, ширина)`. Глибші шари мають менший простір і більше каналів:
перші шари реагують на краї, останні — на «колесо», «голова», «тулуб».

**Чому це важливо для нас:** обчислювальна вартість згортки пропорційна
площі карти ознак. Тому зменшення входу з 640×640 до 320×320 дає
**чотириразове** зменшення обчислень (див. розділ 25).

# 2. Bounding box і системи координат

## Що таке bbox

**Bounding box** (обмежувальна рамка) — прямокутник, який описує, де в кадрі
об'єкт. Це найпростіше представлення локалізації: не контур, не маска, а просто
прямокутник, вирівняний по осях.

## Чотири формати, які плутають усі

| Формат | Поля | Де зустрічається |
|---|---|---|
| **xyxy** | `x1, y1, x2, y2` — лівий-верхній і правий-нижній кути | наш код, `supervision`, torchvision |
| **xywh** | `x1, y1, w, h` — лівий-верхній кут + розміри | COCO, MOT |
| **cxcywh** | `cx, cy, w, h` — центр + розміри | внутрішній вихід YOLO |
| **нормалізований** | те саме, але поділене на ширину/висоту кадру → [0, 1] | YOLO-формат анотацій, наш site-конфіг |

Приклад одного і того ж боксу в кадрі 1280×720:

```
xyxy          : (100, 200, 140, 340)
xywh          : (100, 200,  40, 140)
cxcywh        : (120, 270,  40, 140)
нормалізований cxcywh : (0.0938, 0.375, 0.03125, 0.1944)
```

Переходи:

```
xyxy → cxcywh :  cx = (x1+x2)/2 ,  cy = (y1+y2)/2 ,  w = x2-x1 ,  h = y2-y1
cxcywh → xyxy :  x1 = cx-w/2 ,  y1 = cy-h/2 ,  x2 = cx+w/2 ,  y2 = cy+h/2
```

У нашому коді конверсія з виходу YOLO:

```python
# 🔵 довідкова реалізація
cx, cy, bw, bh = boxes_xywh.T
boxes = np.stack(
    [cx - bw / 2, cy - bh / 2, cx + bw / 2, cy + bh / 2], axis=1
)
```

## Система координат зображення: y вниз

Це найважливіша «дрібниця» в усьому гайді. У математиці вісь **y** зростає
вгору. У зображеннях вона зростає **вниз**: піксель (0,0) — лівий верхній кут.

Наслідок: усі формули з векторними добутками (розділ 18) мають **інвертований**
знак порівняно з підручником. «Ліво» в математичному сенсі візуально стає
«право».

Саме тому наш код не намагається вивести орієнтацію з математики, а просить
перевірити її один раз очима:

```python
# 🟢 src/tcounter/count/geometry.py
"""
Sign convention: ``signed_side`` is the 2-D cross product
``(p2 - p1) x (pt - p1)``.  In a y-up frame a positive value means "left of
the directed line p1 -> p2"; because image y grows downward it means "right
of p1 -> p2" on screen.  Rather than reason about that, name the two
directions in the site config and confirm the mapping once visually with
``tools/draw_lines.py``.
"""
```

Це не лінь — це інженерне рішення. Помилку знаку неможливо побачити в
агрегованих числах: лічильник просто поміняє «туди» і «сюди», і ви виявите це
лише коли графік покаже, що вранці всі йдуть із парку, а не до нього.

# 3. IoU — міра перетину

## Ідея

Треба число, яке каже «наскільки ці два прямокутники — одне й те саме».
Площа перетину сама по собі не годиться: 50 пікселів перетину — це багато для
маленьких боксів і мізер для великих. Тому перетин нормалізують на об'єднання.

**IoU** (Intersection over Union, перетин ділити на об'єднання):

```
IoU(A, B) = площа(A ∩ B) / площа(A ∪ B)
```

Властивості: 0 ≤ IoU ≤ 1. Нуль — не перетинаються зовсім. Один — ідентичні.

## Обчислення

Площа об'єднання не обчислюється напряму — її виражають через перетин:

```
площа(A ∪ B) = площа(A) + площа(B) − площа(A ∩ B)
```

(інакше перетин порахувався б двічі).

Перетин двох прямокутників, вирівняних по осях, сам є прямокутником:

```
ix1 = max(Ax1, Bx1)        iy1 = max(Ay1, By1)
ix2 = min(Ax2, Bx2)        iy2 = min(Ay2, By2)

iw = max(0, ix2 − ix1)     ih = max(0, iy2 − iy1)
перетин = iw · ih
```

`max(0, …)` критичний: якщо прямокутники не перетинаються, різниця буде
від'ємною, і без обрізання ви отримаєте «негативну площу» й безглуздий IoU.

## Простий приклад

```
A = (0, 0, 10, 10)     площа 100
B = (5, 0, 15, 10)     площа 100

ix1 = max(0,5)  = 5     iy1 = max(0,0)  = 0
ix2 = min(10,15)= 10    iy2 = min(10,10)= 10
iw = 5, ih = 10  →  перетин = 50

об'єднання = 100 + 100 − 50 = 150
IoU = 50 / 150 = 0.333
```

Два квадрати, зсунуті на половину сторони, дають IoU ⅓ — корисна опорна точка
для інтуїції. **Зсув на половину ширини — це вже лише 0,33 IoU.** Запам'ятайте
це число, воно знадобиться в розділі 16.

## Наш код

```python
# 🔵 довідкова реалізація, повертається на кроці 46
def iou(a: Box, b: Box) -> float:
    """Intersection over union of two xyxy boxes."""
    ix1, iy1 = max(a[0], b[0]), max(a[1], b[1])
    ix2, iy2 = min(a[2], b[2]), min(a[3], b[3])
    iw, ih = max(0.0, ix2 - ix1), max(0.0, iy2 - iy1)
    inter = iw * ih
    if inter <= 0.0:
        return 0.0
    area_a = max(0.0, a[2] - a[0]) * max(0.0, a[3] - a[1])
    area_b = max(0.0, b[2] - b[0]) * max(0.0, b[3] - b[1])
    union = area_a + area_b - inter
    return inter / union if union > 0.0 else 0.0
```

## Слабке місце IoU, яке нас прямо вб'є

**Якщо бокси не перетинаються, IoU = 0 — і він не каже, наскільки далеко вони
одне від одного.** Бокс на 1 піксель поза перетином і бокс на 500 пікселів
мають однаковий IoU = 0.

Для детекції це нормально. Для **трекінгу на низькому FPS** це катастрофа: усі
кандидати мають нульову схожість, і алгоритм не може вибрати. Саме з цього
народжується розділ 16.

Існують варіанти, що це лікують — **GIoU**, **DIoU** — які додають штраф за
відстань і залишаються інформативними при нульовому перетині. Ми натомість
використовуємо простіший трюк (розділ 17).

# 4. NMS — прибирання дублікатів

## Проблема

Детектор дивиться на кадр у багатьох позиціях і масштабах одночасно. Одна
людина зазвичай спричиняє **десятки** спрацювань — усі приблизно в тому самому
місці, з різною впевненістю.

```
людина
   ↓
 ┌────┐ conf 0.91
 ┌─────┐ conf 0.88
┌────┐  conf 0.85
 ┌───┐  conf 0.62
```

Потрібна одна рамка, а не чотири.

## Алгоритм

**NMS** (Non-Maximum Suppression, подавлення немаксимумів):

```
1. Відсортувати всі бокси за впевненістю, за спаданням.
2. Взяти найвпевненіший — він гарантовано лишається.
3. Викинути всі бокси, що перетинаються з ним сильніше за порог
   (IoU > iou_threshold).
4. Повторити з рештою, поки бокси не закінчаться.
```

Ключова деталь: NMS застосовується **окремо для кожного класу**. Інакше рамка
велосипеда подавила б рамку велосипедиста, бо вони сильно перетинаються — а це
два різні об'єкти, які нам обидва потрібні.

## Наш код

```python
# 🔵 довідкова реалізація, повертається на кроці 27
def nms(boxes: np.ndarray, scores: np.ndarray, iou_threshold: float) -> list[int]:
    """Plain greedy NMS; no torchvision on the edge install."""
    if len(boxes) == 0:
        return []
    x1, y1, x2, y2 = boxes[:, 0], boxes[:, 1], boxes[:, 2], boxes[:, 3]
    areas = np.maximum(0.0, x2 - x1) * np.maximum(0.0, y2 - y1)
    order = scores.argsort()[::-1]          # ← крок 1: сортування за спаданням

    keep: list[int] = []
    while order.size > 0:
        i = int(order[0])                   # ← крок 2: найвпевненіший
        keep.append(i)
        if order.size == 1:
            break
        rest = order[1:]
        ix1 = np.maximum(x1[i], x1[rest])   # ← IoU з усіма рештою одразу
        iy1 = np.maximum(y1[i], y1[rest])
        ix2 = np.minimum(x2[i], x2[rest])
        iy2 = np.minimum(y2[i], y2[rest])
        inter = np.maximum(0.0, ix2 - ix1) * np.maximum(0.0, iy2 - iy1)
        union = areas[i] + areas[rest] - inter
        iou = np.where(union > 0, inter / union, 0.0)
        order = rest[iou <= iou_threshold]  # ← крок 3: подавити схожі
    return keep
```

Зверніть увагу на **векторизацію**: IoU з усіма рештою боксів обчислюється
одним масивним виразом, а не циклом. На Python цикл по 2000 боксів був би
повільніший у десятки разів.

І на окремий виклик для кожного класу:

```python
# 🔵 довідкова реалізація
for class_id in np.unique(class_ids):
    idx = np.where(class_ids == class_id)[0]
    for k in nms(boxes[idx], confidences[idx], self._iou):
        ...
```

## Вибір порогів

Два пороги, які легко переплутати:

- **`conf_threshold`** (у нас 0,35) — мінімальна впевненість, щоб детекція
  взагалі розглядалась. Вище — менше хибних спрацювань, але більше пропусків.
- **`iou_threshold`** (у нас 0,5) — наскільки сильно бокси мусять
  перетинатись, щоб вважатись дублікатами. Нижче — агресивніше подавлення;
  у щільному натовпі це починає з'їдати **справжні** сусідні людей.

Для нас другий важливий: алея з групою людей — саме той випадок, де надто
низький `iou_threshold` зіллє двох пішоходів в одного.

# 5. Метрики детекції: precision, recall, AP, mAP

## Чотири можливі результати

Коли порівнюємо детекції з еталоном (**ground truth**, GT — розмічена людиною
правда):

| | GT: об'єкт є | GT: об'єкта немає |
|---|---|---|
| **Детектор каже «є»** | **TP** (true positive) — вірне спрацювання | **FP** (false positive) — хибне спрацювання |
| **Детектор каже «немає»** | **FN** (false negative) — пропуск | TN — не рахується в детекції |

TN (true negative) у детекції не має сенсу: «правильно не знайшов об'єкт у
кожній позиції, де його нема» — це мільйони випадків.

**Коли детекція вважається TP?** Коли її IoU з GT-рамкою перевищує порог
(зазвичай 0,5). Інакше це одночасно FP (хибна рамка) і FN (пропущений об'єкт).

## Precision і Recall

```
Precision = TP / (TP + FP)      «з того, що я знайшов, скільки правильно?»
Recall    = TP / (TP + FN)      «з того, що було, скільки я знайшов?»
```

Приклад. На кадрі 10 людей. Детектор видав 8 рамок, із них 6 правильні.

```
TP = 6,  FP = 2,  FN = 4

Precision = 6/8  = 0.75
Recall    = 6/10 = 0.60
```

**Між ними завжди компроміс.** Знизьте `conf_threshold` — знайдете більше
справжніх (recall ↑), але й більше сміття (precision ↓). Підніміть — навпаки.

**Для нашого лічильника важливіший recall.** Пропущений пішохід — це −1 у
підрахунку назавжди. Хибна детекція має шанс не дожити до перетину лінії, бо
її вб'є `min_track_len` (розділ 19).

## AP і mAP

Один поріг впевненості — це одна точка (precision, recall). Якщо пройти всі
пороги від 1 до 0, отримаємо **кривую precision-recall**.

**AP** (Average Precision) — площа під цією кривою. Одне число, яке зводить
усю криву:

```
AP = ∫₀¹ p(r) dr        (на практиці — дискретна сума)
```

**mAP** (mean Average Precision) — AP, усереднена по класах.

Позначення, які бачите в таблицях:

- **mAP50** — AP при порозі IoU 0,5. Поблажливий: рамка може бути неточна.
- **mAP50-95** — усереднена по порогах IoU від 0,50 до 0,95 із кроком 0,05
  (10 значень). Суворий: карає за неточну локалізацію.

Для довідки: YOLOv8n має mAP50-95 ≈ 37,3 на COCO при вході 640.

## Матриця невідповідностей

**Confusion matrix** — таблиця «що було × що розпізнали». Рядки — справжній
клас, стовпці — передбачений.

Для нас критична одна клітинка: **пішохід ↔ велосипедист**. Велосипедист, що
веде велосипед поруч, виглядає як пішохід + велосипед. Якщо ці класи
плутаються, групова агрегація з пропозиції (§4) ламається.

Саме тому в кроці 13 плану стоїть «узгодити протокол анотації» — зокрема,
що робити з велосипедистом «пішки».

# 6. Детекція: від R-CNN до YOLO

## Двоетапні детектори

До 2016 детекція працювала у два етапи:

```
Етап 1: згенерувати ~2000 регіонів-кандидатів («тут може бути щось»)
Етап 2: прогнати класифікатор на КОЖНОМУ регіоні окремо
```

Це сімейство **R-CNN** (Regions with CNN features) → Fast R-CNN → Faster R-CNN.
Точно, але повільно: 2000 проходів нейромережі на один кадр. Перші версії
працювали десятки секунд на зображення.

## Одноетапний прорив: YOLO

**YOLO** = **Y**ou **O**nly **L**ook **O**nce — «дивишся лише раз».
Redmon et al., CVPR 2016 ([стаття](https://arxiv.org/abs/1506.02640),
посилання [2] у пропозиції).

Ідея: **переформулювати детекцію як одну задачу регресії**. Один прохід мережі
по кадру одразу віддає всі рамки й усі класи. Не кандидати, не повторні
проходи — одразу відповідь.

Як це працює концептуально:

```
1. Кадр ділиться на сітку S × S (в оригіналі 7 × 7).
2. Кожна клітинка сітки відповідає за об'єкти, чий ЦЕНТР у неї попадає.
3. Кожна клітинка передбачає:
     - B рамок: (x, y, w, h, confidence)
     - розподіл по C класах
4. Усе це — один тензор на виході. Один прохід.
```

Приклад для оригінального YOLO: сітка 7×7, B=2 рамки, C=20 класів →
вихідний тензор 7 × 7 × (2·5 + 20) = 7 × 7 × 30.

**Чому це змінило все:** швидкість зросла на порядки, і детекція стала
реальночасною. Саме це робить наш edge-лічильник можливим. Без одноетапних
детекторів проєкт не існував би.

## Що змінилось до YOLOv8/YOLO11

**Anchor-based → anchor-free.** В оригіналі й у v3–v7 кожна позиція сітки мала
кілька **анкорів** — заготовлених рамок типових пропорцій (високі вузькі для
людей, широкі для машин). Мережа передбачала **поправку** до анкора, а не рамку
з нуля.

Anchor-free (v8, v11) прогнозує рамку напряму від точки сітки. Простіше, не
треба підбирати анкори під датасет, і — важливо для нас — **простіша
постобробка**, бо не треба зберігати й застосовувати таблицю анкорів.

**FPN / багатомасштабність.** Детекція ведеться на кількох рівнях карт ознак
одночасно: дрібна сітка ловить малі об'єкти, груба — великі.

**Розміри моделей.** Ultralytics публікує сімейство:

| Варіант | GFLOPs @640 | mAP50-95 |
|---|---|---|
| **n** (nano) | 8.7 | 37.3 |
| s (small) | 28.6 | 44.9 |
| m (medium) | 78.9 | 50.2 |
| l, x | 165, 258 | 52.9, 53.9 |

Ми беремо **n**. Різниця з «s» — 3,3× обчислень за +7,6 mAP. На нашій задачі
(пішохід у 137–205 пікселів, чиста сцена) ці 7,6 mAP нам не потрібні, а 3,3×
обчислень — критичні.

# 7. Анатомія виходу YOLO

Це розділ, без якого неможливо написати постобробку — і саме тут крок 27 плану
вимагає звірити код із реальною моделлю.

## Форма вихідного тензора

YOLOv8/YOLO11 в режимі детекції віддають **один** тензор:

```
(batch, 4 + n_класів, n_позицій)
```

Для нас: batch = 1, n_класів = 80 (COCO), тобто `(1, 84, N)`.

Скільки позицій N? Детекція ведеться на трьох масштабах — вхід поділений на 8,
16 і 32. Для входу 320:

```
(320/8)²  + (320/16)² + (320/32)²
= 40²     + 20²       + 10²
= 1600    + 400       + 100      = 2100 позицій
```

Отже тензор `(1, 84, 2100)` = 176 400 чисел.

Для входу 640: 80² + 40² + 20² = 6400 + 1600 + 400 = **8400** позицій.

## Що в цих 84 числах

```
індекси 0..3   : cx, cy, w, h   — рамка в пікселях ВХОДУ мережі
індекси 4..83  : оцінки 80 класів
```

Критично: **у v8/v11 немає окремого «objectness»**. У старих YOLO було окреме
число «тут узагалі щось є», яке множилось на оцінку класу. Тепер впевненість
детекції — це просто максимум по класах.

## Постобробка покроково

```python
# 🔵 довідкова реалізація, звірити на кроці 27
raw = np.array(mat_out)          # (84, 2100)
if raw.ndim == 3:
    raw = raw[0]

boxes_xywh  = raw[:4].T          # (2100, 4) — транспонуємо: позиції у рядки
class_scores = raw[4:].T         # (2100, 80)

class_ids    = class_scores.argmax(axis=1)   # який клас найсильніший
confidences  = class_scores.max(axis=1)      # наскільки сильний

keep_mask = confidences >= self._conf        # відсікти слабкі
if not keep_mask.any():
    return []
boxes_xywh  = boxes_xywh[keep_mask]
class_ids   = class_ids[keep_mask]
confidences = confidences[keep_mask]
```

Транспонування `raw[:4].T` — тонке місце. Тензор приходить як «84 рядки по 2100
значень», а нам потрібно «2100 детекцій по 84 значення». Забути транспонування —
значить отримати повну нісенітницю, яка не впаде з помилкою.

Далі — конверсія в xyxy, інверсія letterbox (розділ 8) і NMS по класах
(розділ 4).

## Чому саме тут потрібна обережність

Формат виходу **залежить від того, як модель експортували**. ONNX-експорт може
додати або прибрати transpose, може включити NMS всередину графа, може змінити
порядок осей. Тому крок 27 плану сформульований так:

> Експортувати детектор у ncnn (fp32) і **звірити постобробку** з реальним
> виходом моделі. Код написаний під вихід `(1, 4+nc, n_anchors)`, але не
> перевірений на живій моделі — це перше, що треба підтвердити.

Практична порада: після експорту виведіть `mat_out.shape` і перевірте, що
кількість позицій збігається з формулою вище. Якщо замість 2100 ви бачите 84 —
осі переставлені.

# 8. Letterbox і повернення координат

## Проблема

Мережа приймає квадрат фіксованого розміру (320×320). Наш кадр — 1280×720,
співвідношення 16:9. Якщо просто «розтягнути» до квадрата, люди стануть
товстими й низькими — а мережа навчена на нерозтягнутих людях. Точність падає.

## Letterbox

**Letterbox** — масштабувати, зберігаючи пропорції, і долити поля (padding).

```
Вхідний кадр 1280 × 720,  цільовий розмір 320 × 320

scale = min(320/1280, 320/720) = min(0.25, 0.444) = 0.25
нові розміри: 1280·0.25 = 320,  720·0.25 = 180

Залишається 320 − 180 = 140 пікселів по висоті → поля по 70 зверху й знизу.
```

Результат: зображення 320×180 по центру квадрата 320×320, решта залита
нейтральним сірим (114 — усереднене значення, щоб не створювати фальшивих
краів).

```python
# 🔵 довідкова реалізація
def _letterbox(self, frame: np.ndarray):
    """Resize keeping aspect ratio; returns the mat and the inverse map."""
    h, w = frame.shape[:2]
    size = self._input_size
    scale = min(size / w, size / h)
    new_w, new_h = int(round(w * scale)), int(round(h * scale))
    resized = cv2.resize(frame, (new_w, new_h), interpolation=cv2.INTER_LINEAR)
    canvas = np.full((size, size, 3), 114, dtype=np.uint8)   # нейтральне поле
    pad_x, pad_y = (size - new_w) // 2, (size - new_h) // 2
    canvas[pad_y:pad_y + new_h, pad_x:pad_x + new_w] = resized
    return canvas, scale, pad_x, pad_y
```

## Інверсія — і чому вона критична саме для нас

Мережа віддає координати **у своїй системі** (0…320 з полями). Наша геометрія
підрахунку працює **у пікселях кадру захоплення** (0…1280 × 0…720). Потрібно
повернути:

```
x_кадр = (x_мережа − pad_x) / scale
y_кадр = (y_мережа − pad_y) / scale
```

```python
# 🔵 довідкова реалізація
# Undo the letterbox so boxes land in capture-resolution pixels, the
# coordinate frame the counting geometry works in.
boxes[:, [0, 2]] = (boxes[:, [0, 2]] - pad_x) / scale
boxes[:, [1, 3]] = (boxes[:, [1, 3]] - pad_y) / scale
```

**Чому це не дрібниця.** Якщо забути віднімання `pad_y`, усі бокси зсунуться
вниз на 70/0,25 = 280 пікселів кадру. Лінія підрахунку виявиться не там, де
намальована, і лічильник порахує щось — просто не те. Жодної помилки не впаде.

Це і є причина, чому в плані є **окремий крок 30**:

> Підтвердити, що MAPE на Pi 5 збігається з офлайновим на тих самих кліпах.
> Якщо ні — розбіжність у коді (постобробка, letterbox, пороги), а не в заліза.

# 9. Чому трекінг — окрема задача

Детекція відповідає на питання «де об'єкти **в цьому кадрі**». Вона не має
пам'яті: кожен кадр обробляється з нуля, і між кадрами немає жодного зв'язку.

Для лічильника цього категорично не досить. Розгляньте просту сцену:

```
кадр 1:  [людина на x=100]
кадр 2:  [людина на x=115]
кадр 3:  [людина на x=130]
```

Чисто з детекції неможливо сказати, чи це одна людина, що йде, чи три різні
людини, що по черзі з'явились і зникли. А від цього залежить, порахувати 1 або 3.

**Багатооб'єктний трекінг** (MOT, Multiple Object Tracking) — задача присвоїти
кожному об'єкту **стійкий ідентифікатор** (track ID), який зберігається з кадру
в кадр.

## Tracking-by-detection

Домінуюча парадигма, і саме та, що ми використовуємо:

```
для кожного кадру:
    1. детектор дає набір рамок
    2. АСОЦІАЦІЯ: зіставити ці рамки з уже існуючими треками
    3. неспівставлені рамки → нові треки
    4. неспівставлені треки → можливо, зникли
```

Уся складність — у кроці 2. Решта — бухгалтерія.

## Online vs offline

- **Online** (ми): рішення ухвалюється на кожному кадрі, маючи лише минуле.
  Обов'язково для реального часу.
- **Offline / batch**: можна подивитись усе відео й оптимізувати траєкторії
  глобально. Точніше, але не годиться для живого пристрою.

## Що саме псує трекінг

| Проблема | Що відбувається |
|---|---|
| **Перекриття** (occlusion) | один об'єкт заходить за інший, детекція зникає на кілька кадрів |
| **ID switch** | два треки «обмінялись» ідентичностями при перетині |
| **Фрагментація** | один справжній об'єкт розпався на кілька треків |
| **Пропуски детектора** | об'єкт є, рамки немає |

**Для лічильника найдорожча — фрагментація.** Якщо трек розірвався біля лінії
й відновився з новим ID, ми отримуємо подвійний підрахунок. Саме проти цього
працюють гістерезис і `min_track_len` (розділ 19).

# 10. Задача призначення й угорський алгоритм

## Формулювання

На кадрі є M існуючих треків і N нових детекцій. Треба зіставити їх так, щоб
загальна «несхожість» була мінімальною. Це класична **задача про
призначення** (assignment problem).

Будуємо **матрицю вартості** C розміру M × N:

```
C[i][j] = наскільки погано трек i пояснює детекцію j
```

Для трекінгу по IoU:

```
C[i][j] = 1 − IoU(прогноз_треку_i, детекція_j)
```

Вартість 0 — ідеальний збіг, 1 — не перетинаються зовсім.

Треба знайти таке паросполучення (кожен трек максимум одній детекції й
навпаки), що мінімізує суму вибраних вартостей:

```
minimize  Σᵢ C[i][σ(i)]
```

## Чому не жадібно

Жадібний підхід («бери найменшу вартість, потім наступну найменшу з решти»)
**не оптимальний**. Контрприклад:

```
        д1    д2
т1    0.0   0.5
т2    0.1   1.0
```

**Жадібно:** найменша в усій матриці — 0.0 → т1↔д1. Залишається т2↔д2 = 1.0.
Сума = **1.0**

**Оптимально:** т1↔д2 (0.5) + т2↔д1 (0.1). Сума = **0.6**

Жадібний алгоритм «забрав» д1, яка була значно важливіша для т2.

## Угорський алгоритм

Алгоритм Куна-Манкреса розв'язує задачу **оптимально** за O(n³). Інтуїція:
від рядків і стовпців можна відняти константи, не змінюючи оптимального
розв'язку (бо з кожного рядка вибирається рівно один елемент). Алгоритм
віднімає так, щоб з'явилась достатня кількість нулів, через які й проходить
оптимальне паросполучення.

У Python: `scipy.optimize.linear_sum_assignment`. У `supervision`/ByteTrack —
через бібліотеку `lap`.

## Коли жадібного досить

Різниця між жадібним і оптимальним зростає з кількістю об'єктів і їх
близькістю. На алеї з 1–5 одночасними пішоходами, розділеними помітними
відстанями, вони майже завжди збігаються.

Саме тому наша довідкова реалізація buffered-IoU обрала жадібний варіант —
щоб не тягнути scipy на плату з 1 ГБ пам'яті:

```python
# 🔵 довідкова реалізація, повертається на кроці 46
"""
Association is greedy by descending IoU rather than Hungarian.  On this
scene - a footpath with single-digit simultaneous objects - the two agree
almost always, and greedy keeps the module free of a scipy/lap dependency
so it installs on a 1 GB board.
"""
```

Це задокументоване спрощення, а не недогляд — різниця між «ми це знаємо й
обрали» і «ми цього не знали».

## Гейтування

Перед розв'язанням задачі зазвичай **відсікають** неможливі пари: якщо IoU
менший за порог, пара просто не розглядається.

```python
# 🔵 довідкова реалізація
score = buffered_iou(track_box, det.bbox, self.buffer_scale)
if score >= self.iou_threshold:
    scores.append((score, ci, di))
```

У ByteTrack цей порог називається `minimum_matching_threshold` і за
замовчуванням 0,8 — **на матриці вартості**, тобто вимагає IoU > 0,2.
Це число ще з'явиться в розділі 16.

# 11. Фільтр Калмана

Серце і SORT, і DeepSORT, і ByteTrack. Для нас — важіль №2 у боротьбі з
низьким FPS, тому варто розібратись як слід.

## Задача

Ми хочемо знати, де об'єкт **насправді** і куди він рухається. Маємо лише
шумні вимірювання (рамки детектора «дрижать» на кілька пікселів навіть для
нерухомої людини).

Фільтр Калмана — це **рекурсивний оцінювач**: він тримає поточне уявлення про
стан об'єкта й на кожному кроці
1. **прогнозує**, як стан зміниться,
2. **коригує** прогноз новим вимірюванням,
зважуючи те й інше за їхньою невизначеністю.

## Інтуїція на скалярному випадку

Почнімо з найпростішого: оцінюємо одне число (скажімо, позицію).

- Наша поточна оцінка: `x̂` з невизначеністю `P` (дисперсія).
- Прийшло вимірювання `z` з шумом `R` (дисперсія шуму сенсора).

Нова оцінка — **зважене середнє**:

```
K = P / (P + R)                  ← коефіцієнт Калмана
x̂_нове = x̂ + K · (z − x̂)
P_нове = (1 − K) · P
```

Розберімо `K`:

| Випадок | K | Поведінка |
|---|---|---|
| Сенсор ідеальний, R → 0 | K → 1 | `x̂_нове → z` — повністю віримо вимірюванню |
| Сенсор нікчемний, R → ∞ | K → 0 | `x̂_нове → x̂` — повністю віримо прогнозу |
| R = P | K = 0,5 | просте середнє |

Це і є вся ідея. `(z − x̂)` називають **невідповідністю** або **інновацією** —
наскільки вимірювання здивувало нас.

Числовий приклад: `x̂ = 100`, `P = 4`, прийшло `z = 110`, `R = 4`.

```
K = 4/(4+4) = 0.5
x̂_нове = 100 + 0.5·(110 − 100) = 105
P_нове = (1 − 0.5)·4 = 2        ← невизначеність ЗМЕНШИЛАСЬ
```

Оцінка посередині, і ми тепер упевненіші, ніж до вимірювання. Два незалежні
джерела інформації завжди дають менше невизначеності, ніж кожне окремо.

## Повна матрична форма

У реальності стан — вектор (позиція **і** швидкість), тому все стає матричним.

**Позначення:**

| Символ | Що це | Розмір |
|---|---|---|
| `x` | вектор стану | n×1 |
| `P` | коваріаційна матриця стану (наша невпевненість) | n×n |
| `F` | матриця переходу стану (модель руху) | n×n |
| `Q` | коваріація шуму процесу (наскільки модель неточна) | n×n |
| `z` | вектор вимірювання | m×1 |
| `H` | матриця вимірювання (стан → що ми бачимо) | m×n |
| `R` | коваріація шуму вимірювання | m×m |
| `K` | коефіцієнт Калмана | n×m |

**Крок прогнозу** (predict) — що буде, якщо нічого не вимірювати:

```
x̂ₖ⁻ = F · x̂ₖ₋₁
Pₖ⁻ = F · Pₖ₋₁ · Fᵀ + Q
```

Перше рівняння просто рухає стан за моделлю. Друге — **невизначеність завжди
зростає**: `F P Fᵀ` переносить її, `+ Q` додає нову через неточність моделі.
Без вимірювань фільтр «розмиває» своє уявлення.

**Крок корекції** (update) — вбираємо вимірювання:

```
yₖ = zₖ − H · x̂ₖ⁻                    ← інновація (невідповідність)
Sₖ = H · Pₖ⁻ · Hᵀ + R                 ← коваріація інновації
Kₖ = Pₖ⁻ · Hᵀ · Sₖ⁻¹                  ← коефіцієнт Калмана
x̂ₖ = x̂ₖ⁻ + Kₖ · yₖ                   ← скоригований стан
Pₖ = (I − Kₖ · H) · Pₖ⁻               ← скоригована невизначеність
```

Порівняйте з скалярним випадком: `Kₖ = Pₖ⁻Hᵀ(HPₖ⁻Hᵀ + R)⁻¹` — та сама
структура «наша невпевненість поділена на суму невпевненостей».

## Модель постійної швидкості

Найпоширеніша модель руху. Стан — позиція й швидкість:

```
x = [ p ]
    [ v ]
```

За час Δt позиція зміниться на `v·Δt`, швидкість — не зміниться:

```
      [ 1  Δt ]
F  =  [ 0   1 ]
```

Перевірка: `F·x = [p + v·Δt, v]ᵀ`. Так і має бути.

Ми вимірюємо лише позицію, не швидкість:

```
H = [ 1   0 ]
```

**Швидкість ніколи не вимірюється напряму — вона виводиться** з послідовності
позицій. Це важливо: щоб фільтр дізнався швидкість, йому потрібно **щонайменше
два вимірювання**, а щоб оцінка стала надійною — три-чотири.

Запам'ятайте цей факт. У розділі 16 він стане критичним: велосипедист,
який перебуває в кадрі лише 4 кадри, фізично не встигає дати фільтру
достатньо даних.

## Стан у SORT

SORT використовує **семивимірний** стан:

```
x = [ u,  v,  s,  r,  u̇,  v̇,  ṡ ]ᵀ

u, v — координати центру рамки
s    — площа (масштаб)
r    — співвідношення сторін (aspect ratio)
u̇, v̇ — швидкості центру
ṡ    — швидкість зміни площі
```

Тонкість: **`r` не має похідної**. SORT припускає, що співвідношення сторін
об'єкта постійне. Для пішохода це розумно (людина не стає ширшою, йдучи), і це
економить вимір стану.

`ṡ` є, бо об'єкт, що наближається до камери, росте в кадрі — площа змінюється
закономірно, і це варто моделювати.

## Що це дає трекінгу

Три різні речі:

1. **Згладжування.** Дрижання детектора на ±3 пікселі усереднюється.
2. **Прогноз для асоціації.** Замість «де трек був» порівнюємо «де трек
   **має бути**» з новою детекцією. На швидкому руху це єдине, що працює.
3. **Переживання пропусків.** Якщо детекція зникла на 2 кадри, фільтр
   продовжує прогнозувати (з ростом невизначеності), і трек не вмирає.

У нашій довідковій реалізації використано спрощену версію — без повної
коваріації, лише згладжена швидкість:

```python
# 🔵 довідкова реалізація, повертається на кроці 46
def _absorb(self, cand: _Candidate, det: Detection) -> None:
    old_cx = (cand.box[0] + cand.box[2]) * 0.5
    old_cy = (cand.box[1] + cand.box[3]) * 0.5
    new_cx = (det.bbox[0] + det.bbox[2]) * 0.5
    new_cy = (det.bbox[1] + det.bbox[3]) * 0.5
    steps = max(1, cand.age_since_update + 1)
    measured = ((new_cx - old_cx) / steps, (new_cy - old_cy) / steps)

    if cand.hits == 1:
        cand.velocity = measured          # перше вимірювання швидкості
    else:
        a = self.velocity_smoothing       # експоненційне згладжування
        cand.velocity = (
            a * measured[0] + (1 - a) * cand.velocity[0],
            a * measured[1] + (1 - a) * cand.velocity[1],
        )
```

Рядок `if cand.hits == 1` — це рівно той момент, коли швидкість стає відома
вперше. До нього прогноз неможливий.

І прогноз:

```python
# 🔵 довідкова реалізація
def predicted(self, use_prediction: bool) -> Box:
    if not use_prediction:
        return self.box
    vx, vy = self.velocity
    steps = self.age_since_update + 1     # скільки кадрів без вимірювання
    x1, y1, x2, y2 = self.box
    return (x1 + vx * steps, y1 + vy * steps, x2 + vx * steps, y2 + vy * steps)
```

`steps` враховує, що трек міг не оновлюватись кілька кадрів — тоді прогноз
екстраполюється далі.

# 12. SORT

**SORT** = **S**imple **O**nline and **R**ealtime **T**racking.
Bewley et al., ICIP 2016 ([стаття](https://arxiv.org/abs/1602.00763),
посилання [4] у пропозиції). Baseline (b) у нашому оцінюванні.

## Головна теза

Ідентичність можна тримати **без жодної інформації про зовнішній вигляд** —
лише на геометрії й руху. Три класичні інструменти, нуль навчання:

```
Фільтр Калмана   →  прогноз, де трек буде
IoU              →  міра схожості прогнозу з детекцією
Угорський алгоритм →  оптимальне зіставлення
```

## Повний цикл

```
для кожного кадру:
    1. PREDICT: кожен трек прогнозує свою рамку фільтром Калмана
    2. COST:    C[i][j] = 1 − IoU(прогноз_i, детекція_j)
    3. GATE:    пари з IoU < iou_threshold відкидаються
    4. MATCH:   угорський алгоритм на матриці C
    5. UPDATE:  співставлені треки коригуються (крок корекції Калмана)
    6. BIRTH:   неспівставлені детекції → нові треки
    7. DEATH:   треки без оновлення довше max_age → видаляються
```

## Параметри

| Параметр | Типово | Що робить |
|---|---|---|
| `max_age` | 1–30 | скільки кадрів трек живе без детекції |
| `min_hits` | 3 | скільки підтверджень потрібно, щоб трек «вважався» |
| `iou_threshold` | 0,3 | гейт асоціації |

`min_hits` — захист від шуму: одноразове хибне спрацювання не створить
«людину». Але для нас це пастка: на низькому FPS велосипедист може взагалі не
набрати 3 підтверджень (розділ 16).

## Швидкість і слабке місце

SORT працює на сотнях Hz — обчислення нехтовно малі порівняно з детектором.

**Слабке місце:** без зовнішнього вигляду, коли двоє людей перетинаються або
хтось зникає за перешкодою, геометрія стає неоднозначною, і ідентичності
переплутуються. Це ті самі ID switch із розділу 9.

# 13. DeepSORT і re-ідентифікація

**DeepSORT.** Wojke et al., ICIP 2017
([стаття](https://arxiv.org/abs/1703.07402), посилання [5] у пропозиції).

## Що додає

Маленьку CNN, яка для кожної детекції видає **вектор зовнішнього вигляду**.

**Embedding** (вектор вкладення) — це список чисел фіксованої довжини
(наприклад 128), який кодує «як виглядає» об'єкт. Мережа навчена так, щоб
**два зображення однієї людини давали близькі вектори, а різних людей —
далекі**. Такі мережі навчають на задачі **re-ідентифікації** (re-ID):
«чи це та сама людина?».

Приклад концептуально:

```
людина в червоній куртці, кадр 10  →  [0.21, −0.88, 0.05, ...]
та сама людина, кадр 40            →  [0.19, −0.91, 0.07, ...]   близько
інша людина в синьому              →  [−0.73, 0.12, 0.66, ...]   далеко
```

## Міра схожості: косинусна відстань

Для векторів вкладення використовують не евклідову, а **косинусну** відстань —
бо важливий напрямок вектора, не його довжина:

```
cos_similarity(a, b) = (a · b) / (‖a‖ · ‖b‖)

cos_distance(a, b) = 1 − cos_similarity(a, b)
```

де `a · b = Σ aᵢbᵢ` — скалярний добуток, `‖a‖ = √(Σ aᵢ²)` — довжина вектора.

Діапазон відстані: 0 (ідентичні напрямки) … 2 (протилежні). На нормалізованих
векляках зазвичай 0…1.

## Відстань Махаланобіса

DeepSORT також використовує **відстань Махаланобіса** для геометричної частини —
це відстань, нормалізована на невизначеність фільтра Калмана:

```
d²(z, x̂) = (z − H x̂)ᵀ · S⁻¹ · (z − H x̂)
```

де `S` — коваріація інновації з розділу 11. Сенс: відхилення на 10 пікселів
«дешеве», якщо фільтр і сам невпевнений, і «дороге», якщо впевнений.
Це розумніше за просту евклідову відстань.

Фінальна вартість — зважена комбінація:

```
C[i][j] = λ · d_махаланобіса + (1 − λ) · d_косинусна
```

## Чому ми його не беремо

На кожну детекцію треба прогнати **додаткову нейромережу**. Якщо в кадрі
10 людей — це 10 прогонів re-ID мережі на кадр, зверху детектора.

На Pi 5 це з'їло б більшу частину бюджету FPS, а FPS для нас — не комфорт, а
жорстке обмеження на те, які класи взагалі можна рахувати. Тому пропозиція
цитує DeepSORT як історичний крок, але не використовує.

# 14. ByteTrack

**ByteTrack.** Zhang et al., ECCV 2022
([стаття](https://arxiv.org/abs/2110.06864), посилання [6] у пропозиції).
**Наш основний трекер.**

## Спостереження, на якому все тримається

Детектор видає рамки з оцінками впевненості. Стандартна практика — відкинути
все, що нижче порога (скажімо 0,5), бо низька впевненість зазвичай означає шум.

**Але:** частково перекрита людина дає рамку з **низькою** впевненістю. Це не
шум — це реальна людина, яку просто погано видно.

```
кадр 10: людина добре видна        conf 0.91   ← беремо
кадр 11: зайшла за стовп наполовину conf 0.34   ← ВИКИДАЄМО
кадр 12: знову добре видна          conf 0.88   ← беремо, але вже НОВИЙ трек
```

Відкидаючи кадр 11, ми рвемо трек саме там, де найважче. Для лічильника це
подвійний підрахунок.

## Рішення: асоціація у два проходи

```
Вхід: детекції D, пороги τ_high (0.5) і τ_track (0.25)

1. РОЗДІЛИТИ:
     D_high = { d ∈ D : conf(d) ≥ τ_high }
     D_low  = { d ∈ D : τ_track ≤ conf(d) < τ_high }

2. ПРОГНОЗ: усі треки T прогнозують рамки фільтром Калмана

3. ПЕРША АСОЦІАЦІЯ: T ↔ D_high  (угорський алгоритм по IoU)
     → T_matched, T_unmatched, D_high_unmatched

4. ДРУГА АСОЦІАЦІЯ: T_unmatched ↔ D_low        ← НОВИЗНА
     Треки, які не знайшли високовпевненої пари, пробують низьковпевнені.
     → ще частина треків врятована

5. НОВІ ТРЕКИ: лише з D_high_unmatched
     Низьковпевнена детекція НІКОЛИ не створює новий трек —
     лише продовжує існуючий.

6. ВИДАЛЕННЯ: треки без оновлення довше lost_track_buffer
```

**Крок 5 — це те, що робить метод безпечним.** Низька впевненість приймається
як доказ «цей трек продовжується», але не як доказ «тут з'явився новий
об'єкт». Асиметрія навмисна: продовжити існуючий трек — слабке твердження,
створити новий — сильне.

Звідси назва статті: *«associating every detection box»* — асоціюючи **кожну**
рамку. «BYTE» — від цього принципу.

## Чому це безкоштовно

Жодної додаткової нейромережі. Усе, що додалось — один додатковий виклик
угорського алгоритму на меншій матриці. Обчислювально це ніщо порівняно з
детектором.

**Результат:** надійність рівня DeepSORT без його ціни. Саме тому пропозиція
обрала його: щільні групи людей — рівно наш випадок, а коштує це нуль.

## Параметри в нашому конфізі

```yaml
# 🟢 configs/site_ucu_alley.yaml
tracker:
  backend: bytetrack
  # ByteTrack's published defaults assume ~30 FPS, which is why Pi 5 at 320
  # can use them unchanged (plan section 3).
  track_activation_threshold: 0.25   # τ_track — нижня межа другого проходу
  lost_track_buffer: 30              # скільки кадрів тримати втрачений трек
  minimum_matching_threshold: 0.8    # гейт на матриці вартості → IoU > 0.2
  frame_rate: 30
```

**`lost_track_buffer: 30` — це 30 кадрів, не 30 секунд.** На 30 FPS це 1 секунда.
На 6 FPS — 5 секунд, що абсурдно довго: трек «висітиме» й може підхопити
зовсім іншу людину. Параметри, виражені в кадрах, треба перераховувати при
зміні FPS. Це одна з причин, чому ми вибрали залізо, що дає 30 FPS.

## Наш адаптер

ByteTrack ми не реалізовуємо — беремо з `supervision`:

```python
# 🟢 src/tcounter/track/bytetrack.py
class ByteTrackTracker:
    def __init__(self, track_activation_threshold=0.25, lost_track_buffer=30,
                 minimum_matching_threshold=0.8, frame_rate=30):
        import supervision as sv
        self._sv = sv
        self._kwargs = dict(...)
        self._tracker = sv.ByteTrack(**self._kwargs)

    def update(self, detections, frame_idx=0) -> list[Track]:
        tracked = self._tracker.update_with_detections(to_supervision(detections))
        out: list[Track] = []
        if tracked.tracker_id is None:
            return out
        for i, tid in enumerate(tracked.tracker_id):
            x1, y1, x2, y2 = tracked.xyxy[i]
            out.append(Track(track_id=int(tid), bbox=(...), ...))
        return out
```

Шар-адаптер існує, щоб решта коду не знала про `supervision`. Це дає
взаємозамінність бекендів — підміна детектора не чіпає логіку підрахунку.

# 15. Життєвий цикл треку

Трек не просто «є» або «немає» — у нього є стани, і від правил переходу
залежить, порахуємо ми людину чи ні.

```
                 перша детекція
                       ↓
                 ┌───────────┐
                 │ TENTATIVE │  (новий, недовірений)
                 └───────────┘
                   ↓        ↓
       min_hits    │        │  пропущено до підтвердження
       підтверджень│        ↓
                   ↓     ┌─────────┐
            ┌───────────┐│ DELETED │
            │ CONFIRMED │└─────────┘
            └───────────┘
              ↓       ↑
    немає     │       │ знову знайдено
    детекції  ↓       │
            ┌──────┐──┘
            │ LOST │
            └──────┘
                ↓  понад max_age / lost_track_buffer
            ┌─────────┐
            │ DELETED │
            └─────────┘
```

**Чому це важливо для нас.** Лічильник бачить лише `CONFIRMED` треки. Тому:

- якщо `min_hits` завеликий, швидкі об'єкти не встигають підтвердитись і
  **зникають із підрахунку безслідно**;
- якщо `max_age` завеликий, мертвий трек може «підхопити» іншу людину →
  фальшива траєкторія → можливий хибний перетин.

Наш код веде свій паралельний облік, бо лічильнику потрібна не лише поточна
рамка, а й історія:

```python
# 🟢 src/tcounter/count/counter.py
@dataclass
class _TrackState:
    n_obs: int = 0                 # скільки разів бачили → для min_track_len
    conf_sum: float = 0.0          # сума впевненостей → для conf_mean у події
    last_seen_frame: int = -1      # для прибирання старих станів
    class_id: int = -1
    class_name: str | None = None
    lines: dict[str, _LineState] = field(default_factory=dict)

    @property
    def conf_mean(self) -> float:
        return self.conf_sum / self.n_obs if self.n_obs else 0.0
```

І прибирає застарілі, щоб багатоденний прогін не з'їв пам'ять:

```python
# 🟢 src/tcounter/count/counter.py
def _expire(self, frame_idx: int) -> None:
    idle = self.config.max_track_idle
    stale = [
        tid for tid, st in self._tracks.items()
        if frame_idx - st.last_seen_frame > idle
    ]
    for tid in stale:
        del self._tracks[tid]
```

# 16. Наша математика: FPS і асоціація

Це найважливіший розділ гайда. Тут виводиться результат, якого немає в жодній
із цитованих статей, і який визначив вибір заліза для проєкту.

## Питання

Яка мінімальна частота кадрів потрібна, щоб IoU-асоціація взагалі працювала
для об'єкта, що рухається зі швидкістю `v`?

## Виведення

Нехай:
- `v` — швидкість об'єкта, м/с
- `w` — реальна ширина об'єкта, м
- `f` — частота кадрів, кадрів/с

**Крок 1. Зсув за один кадр.** Між двома послідовними кадрами проходить `1/f`
секунд, отже об'єкт зміщується на

```
d = v / f          [метрів]
```

**Крок 2. Умова перетину.** Два прямокутники однакової ширини `w`, зсунуті по
горизонталі на `d`, перетинаються тоді й лише тоді, коли зсув менший за ширину:

```
d < w
```

**Крок 3. Підставляємо:**

```
v / f < w     ⟹     f > v / w
```

```
╔═══════════════════════╗
║   f_min = v / w       ║
╚═══════════════════════╝
```

## Уточнення: порог IoU, а не просто перетин

Трекери вимагають не будь-якого перетину, а IoU вище порога `τ`. Виведемо
точніше.

Два бокси `w × h`, зсунуті по горизонталі на `d` (без вертикального зсуву):

```
перетин     = (w − d) · h
об'єднання  = w·h + w·h − (w−d)·h = h·(2w − w + d) = h·(w + d)

IoU = (w − d)·h / (h·(w + d)) = (w − d) / (w + d)
```

Гарна формула: висота скорочується, IoU залежить лише від відношення зсуву до
ширини.

Прирівнюємо до порога й розв'язуємо щодо `d`:

```
(w − d)/(w + d) = τ
w − d = τw + τd
w(1 − τ) = d(1 + τ)
d = w · (1 − τ)/(1 + τ)
```

Підставляємо `d = v/f`:

```
╔═══════════════════════════════════════╗
║        v        1 + τ                 ║
║  f >  ───  ·  ─────────               ║
║        w        1 − τ                 ║
╚═══════════════════════════════════════╝
```

Перевірка граничних випадків:
- `τ = 0` → множник 1 → `f > v/w` ✓ збігається з простим виведенням
- `τ = 0,2` → множник `1,2/0,8 = 1,5` → **звідси той «×1,5»**, що я згадував
- `τ = 0,5` → множник `1,5/0,5 = 3`

## Числа для наших класів

Беремо ширину по плечах для людини ≈ 0,55 м, ширину автомобіля ≈ 1,8 м.
Порог ByteTrack `minimum_matching_threshold = 0,8` на матриці вартості
означає IoU > 0,2, тобто `τ = 0,2` і множник 1,5.

| Об'єкт | v, м/с | w, м | f_min (τ=0) | f_min (τ=0,2) |
|---|---|---|---|---|
| Пішохід | 1,4 | 0,55 | 1,4/0,55 = **2,5** | ×1,5 = **3,8** |
| **Велосипедист** | **5,0** | **0,55** | 5,0/0,55 = **9,1** | ×1,5 = **13,6** |
| Автомобіль | 14,0 | 1,8 | 14/1,8 = **7,8** | ×1,5 = **11,7** |

## Висновок №1: велосипедист складніший за автомобіль

Контрінтуїтивно, але прямо з формули: автомобіль утричі швидший, але **втричі
ширший**, і ширина компенсує швидкість. Велосипедист — найгірший випадок, бо
він вузький **і** швидкий.

Це варте окремого рядка у фінальному звіті: «найважчий клас для асоціації — не
найшвидший, а той, у якого найгірше відношення швидкості до ширини».

## Висновок №2: інваріантність до масштабу

Найважливіше. Покажемо, що **ні зум, ні роздільна здатність не допомагають**.

Нехай `k` — метрів на піксель (залежить від зуму, відстані й роздільної
здатності). Тоді в пікселях:

```
зсув  d_px = (v/f) / k
ширина w_px = w / k
```

Відношення, яке й визначає IoU:

```
d_px     (v/f)/k      v/f       v
──── =  ─────────  =  ───  =  ─────
w_px      w/k          w       f·w
```

**`k` скоротився.** Відношення зсуву до ширини не залежить від масштабу зовсім.

Практично: при f=12 мм на кадрі 640 пікселів велосипедист на 6 FPS зсувається
на **50 пікселів при ширині боксу 33 пікселі**. Подвойте роздільну здатність —
буде 100 пікселів зсуву при 66 пікселях ширини. Те саме відношення, та сама
нульова IoU.

```
Залишається рівно три важелі:
   1. частота кадрів  f
   2. прогноз руху (фільтр Калмана)
   3. сама метрика асоціації (замість чистого IoU)
```

## Висновок №3: чому прогноз Калмана не рятує повністю

Прогноз **міг би** компенсувати зсув: якщо знаємо швидкість, прогнозована рамка
опиниться там, де об'єкт, і IoU буде високим.

Але (розділ 11) **швидкість треба спершу виміряти** — потрібно 2–3 спостереження.
А скільки кадрів велосипедист узагалі перебуває в кадрі?

При f=12 мм покриття кадру 10,6 м, велосипедист 5 м/с:

```
час у кадрі = 10,6 / 5 = 2,1 с

при  6 FPS →  2,1 · 6  ≈   13 кадрів ... але перші 2-3 йдуть на ініціалізацію
при  2 FPS →  2,1 · 2  ≈    4 кадри   ← не встигає взагалі
при 30 FPS →  2,1 · 30 ≈   63 кадри   ← з запасом
```

На низькому FPS трек витрачає весь свій час на ініціалізацію й гине до того, як
прогноз почне працювати.

## Наслідок для вибору заліза

| Платформа | Реальний FPS | Пішохід (3,8) | Велосипедист (13,6) | Автомобіль (11,7) |
|---|---|---|---|---|
| Pine A64+ 1GB | 3–6 | на межі | ✗ **неможливо** | ✗ |
| **Raspberry Pi 5** | **30–40** | запас ×8 | **запас ×2,5** | запас ×3 |

Саме цей розрахунок — причина переходу з Pine A64 на Pi 5. Не «хочеться
швидше», а «на Pine A64 клас велосипедистів із пропозиції недосяжний
математично, і це не лікується тюнінгом».

Бонус від Pi 5: ByteTrack працює на **дефолтних** гіперпараметрах, бо вони й
розраховані під ~30 FPS.

## Що з цього роблять на кроці 33 плану

> **Емпірично знайти поріг розвалу асоціації:** штучно обмежити FPS на Pi 5 і
> зафіксувати, де треки велосипедистів починають фрагментуватись.
> Передбачення — 9,1 / 13,6 FPS.

Тобто виведена формула перетворюється на **передбачення, яке перевіряється
експериментом** — і це окремий результат для звіту, який дістається безкоштовно.

# 17. Buffered IoU

Третій важіль із попереднього розділу: змінити саму метрику асоціації.

## Ідея

Якщо бокси не перетинаються — роздуймо їх, поки не почнуть.

**Buffered IoU** (підхід C-BIoU): перед обчисленням IoU збільшити обидва бокси
на частку їхнього власного розміру.

```
w' = w · (1 + s)
h' = h · (1 + s)
```

де `s` — коефіцієнт буфера (`buffer_scale` у коді). `s = 0` → звичайний IoU.

Роздування центроване: бокс росте в усі боки, центр не рухається.

```python
# 🔵 довідкова реалізація, повертається на кроці 46
def inflate(box: Box, scale: float) -> Box:
    """Grow a box by `scale` of its own width and height, centred."""
    if scale <= 0.0:
        return box
    x1, y1, x2, y2 = box
    dw = (x2 - x1) * scale * 0.5     # половина приросту з кожного боку
    dh = (y2 - y1) * scale * 0.5
    return (x1 - dw, y1 - dh, x2 + dw, y2 + dh)


def buffered_iou(track_box: Box, det_box: Box, scale: float) -> float:
    return iou(inflate(track_box, scale), inflate(det_box, scale))
```

## Математика

Умова перетину тепер `d < w(1+s)`, отже:

```
╔═════════════════════════════╗
║            v                ║
║  f  >  ───────────          ║
║         w · (1 + s)         ║
╚═════════════════════════════╝
```

Буфер **прямо дільник** у вимозі до FPS. Це дає нам важіль там, де FPS
підняти неможливо.

**Скільки буфера потрібно для велосипедиста на 6 FPS?**

```
Треба:  w(1+s) > v/f = 5/6 = 0,833 м
        0,55 · (1+s) > 0,833
        1 + s > 1,515
        s > 0,515
```

З порогом IoU:

```
            v        1 + τ
f  >  ───────────  · ─────
       w · (1+s)     1 − τ
```

## Числова перевірка

Сцена Pine A64: бокс 33 × 137 пікселів, зсув 50 пікселів.

**Без буфера:** перетину немає, IoU = 0.

**З `s = 1,0`:** бокси стають 66 × 274.

```
перетин по x = 66 − 50 = 16
перетин      = 16 · 274 = 4 384
площа кожного = 66 · 274 = 18 084
об'єднання   = 2·18 084 − 4 384 = 31 784
IoU = 4 384 / 31 784 = 0,138          ← гейт 0,15 НЕ проходить, на межі
```

**З `s = 2,0`:** бокси 99 × 411.

```
перетин по x = 99 − 50 = 49
перетин      = 49 · 411 = 20 139
площа кожного = 99 · 411 = 40 689
об'єднання   = 2·40 689 − 20 139 = 61 239
IoU = 20 139 / 61 239 = 0,329          ← проходить із запасом
```

Тому в довідковій реалізації для цього випадку стоїть `buffer_scale=2.0`.

## Ціна

Буфер не безкоштовний: роздуті бокси перетинаються легше — **в тому числі
з чужими**. У щільному натовпі великий буфер почне плутати сусідів, бо
«всі перетинаються з усіма».

Тобто `buffer_scale` — це компроміс:

```
малий s  →  втрачаємо швидкі об'єкти (фрагментація)
великий s →  плутаємо сусідні об'єкти (ID switch)
```

Оптимум залежить від щільності сцени й FPS, тому це параметр для **ablation**
(крок 46), а не фіксована константа.

## Два окремі важелі — навмисно

Довідкова реалізація розділяє буфер і прогноз двома незалежними
перемикачами, щоб у ablation можна було виміряти внесок кожного окремо:

```python
# 🔵 довідкова реалізація
"""
``buffer_scale``
    Inflate both track and detection boxes by this fraction of their size
    before computing IoU (the C-BIoU idea).  ``0.0`` degrades to plain IoU,
    which is the baseline to compare against.

``use_prediction``
    Advance each track by its estimated constant velocity before matching.
    ``False`` isolates how much the buffer alone buys.
"""
```

Це і є правильний дизайн експерименту: один клас, два незалежні перемикачі,
чотири комбінації — замість чотирьох різних реалізацій, які не порівняти.

# 18. Геометрія підрахунку

Тут починається **наш власний внесок**. Усе попереднє — готові цеглини з
літератури. Шару підрахунку з перетинів ліній немає в жодній із цитованих
статей.

## Задача

Дано: траєкторія треку — послідовність точок. Дано: лінія підрахунку —
**відрізок** між двома точками. Питання: чи перетнув трек лінію, і в якому
напрямку?

## Векторний добуток у 2D

Фундамент усього розділу. Для трьох точок A, B, C визначимо:

```
orient(A, B, C) = (Bx − Ax)·(Cy − Ay) − (By − Ay)·(Cx − Ax)
```

Це **z-компонента векторного добутку** `(B−A) × (C−A)`. Геометричний сенс:
величина дорівнює **подвоєній площі трикутника ABC зі знаком**.

Знак каже, з якого боку від прямої A→B лежить точка C:

```
orient > 0  →  C злiва від A→B   (у системі з y вгору)
orient = 0  →  A, B, C колінеарні
orient < 0  →  C справа
```

**Пам'ятайте про y вниз** (розділ 2): на екрані «зліва» й «справа» міняються
місцями.

```python
# 🟢 src/tcounter/count/geometry.py
def _orientation(a: Point, b: Point, c: Point) -> float:
    """Cross product (b - a) x (c - a). Sign gives the turn direction."""
    return (b[0] - a[0]) * (c[1] - a[1]) - (b[1] - a[1]) * (c[0] - a[0])
```

### Простий приклад

Лінія від (0,0) до (10,0) — горизонтальна. Точка (5, 5):

```
orient((0,0), (10,0), (5,5)) = (10−0)·(5−0) − (0−0)·(5−0) = 50 − 0 = 50 > 0
```

Точка (5, −5):

```
orient((0,0), (10,0), (5,−5)) = 10·(−5) − 0·5 = −50 < 0
```

Різні знаки — різні боки. Саме це потрібно.

## З якого боку лінії точка

```python
# 🟢 src/tcounter/count/geometry.py
def signed_side(self, pt: Point) -> float:
    """Cross product; sign says which side of the line pt is on."""
    return _orientation(self.p1, self.p2, pt)
```

## Перпендикулярна відстань

Знак сам по собі не каже, **наскільки далеко** точка від лінії. А нам потрібно:
смуга гістерезису задається в пікселях.

Виведення просте. Площа трикутника через основу й висоту:

```
площа = ½ · основа · висота
```

Основа — довжина лінії `L = |p2 − p1|`. А `|orient|` — подвоєна площа. Отже:

```
|orient| = 2 · площа = основа · висота = L · h

         orient
h  =  ──────────        ← зі знаком
          L
```

```python
# 🟢 src/tcounter/count/geometry.py
def perp_distance(self, pt: Point) -> float:
    """Signed perpendicular distance from pt to the line, in pixels.

    The hysteresis band in count.counter is expressed in these units, so
    it stays meaningful independently of how long the line is.
    """
    length = self.length
    if length < 1e-9:
        return 0.0
    return self.signed_side(pt) / length
```

**Нормалізація на довжину — не косметика.** Без неї `signed_side` масштабувався
б із довжиною лінії: та сама точка дала б «відстань» 30 для короткої лінії й
3000 для довгої. Смуга гістерезису `hysteresis_px = 8` стала б безглуздою.

Є тест рівно на це:

```python
# 🟢 tests/test_geometry.py
def test_perp_distance_is_in_pixels_and_signed():
    # Distance must not depend on how long the line is: the hysteresis band
    # in CounterConfig is expressed in these units.
    assert GATE.perp_distance((100.0, 130.0)) == pytest.approx(30.0)
    assert GATE.perp_distance((100.0, 70.0)) == pytest.approx(-30.0)
    long_gate = Line("l", (0.0, 100.0), (5000.0, 100.0))
    assert long_gate.perp_distance((100.0, 130.0)) == pytest.approx(30.0)
```

## Головна помилка: пряма vs відрізок

Тут найважливіше місце в усьому гайді з точки зору коректності.

**Наївна реалізація:** «якщо знак `signed_side` змінився між кадрами — значить
перетнув».

**Чому це неправильно.** `signed_side` описує **нескінченну пряму**, яка
проходить через `p1` і `p2`. Пряма продовжується за обидва кінці відрізка
нескінченно далеко.

```
                              ┆
         p1 ━━━━━━━━━━━ p2    ┆  ← продовження прямої
         (намальована лінія)   ┆
                              ┆
                         людина│йде тут
                              ┆
```

Людина на `x = 400` при відрізку від `x = 0` до `x = 200` **ніколи не
проходить через ворота** — але знак `signed_side` змінюється точно так само, як
при справжньому перетині. Наївний лічильник її порахує.

Це рівно та помилка, через яку ми не використовуємо `supervision.LineZone`.

## Правильна перевірка: перетин відрізків

Два відрізки `A₁A₂` і `B₁B₂` перетинаються тоді, коли **кожен з них розділяє
кінці іншого**:

```
d1 = orient(B1, B2, A1)
d2 = orient(B1, B2, A2)      ← A1 і A2 по різні боки від B-прямої?
d3 = orient(A1, A2, B1)
d4 = orient(A1, A2, B2)      ← B1 і B2 по різні боки від A-прямої?

Перетин ⟺  знак(d1) ≠ знак(d2)  І  знак(d3) ≠ знак(d4)
```

Інтуїція: якщо тільки перша умова виконана, відрізок A перетинає **пряму** B,
але, можливо, за межами самого відрізка B. Потрібні обидві умови.

Плюс окремо — **колінеарні** випадки, коли якийсь `d` дорівнює нулю: точка
лежить на прямій, і треба перевірити, чи вона в межах відрізка.

```python
# 🟢 src/tcounter/count/geometry.py
def segments_intersect(a1: Point, a2: Point, b1: Point, b2: Point,
                       eps: float = 1e-9) -> bool:
    """True when the closed segments a1-a2 and b1-b2 share at least one point.

    This is the test that distinguishes a real crossing from a track passing
    by the *extension* of the counting line.  A sign flip of ``signed_side``
    alone is not enough: the infinite line extends past both endpoints, so a
    pedestrian walking well outside the counted gate would flip the sign and
    be counted.
    """
    d1 = _orientation(b1, b2, a1)
    d2 = _orientation(b1, b2, a2)
    d3 = _orientation(a1, a2, b1)
    d4 = _orientation(a1, a2, b2)

    if ((d1 > eps and d2 < -eps) or (d1 < -eps and d2 > eps)) and (
        (d3 > eps and d4 < -eps) or (d3 < -eps and d4 > eps)
    ):
        return True

    # Collinear / touching cases.
    if abs(d1) <= eps and _on_segment(b1, b2, a1):
        return True
    if abs(d2) <= eps and _on_segment(b1, b2, a2):
        return True
    if abs(d3) <= eps and _on_segment(a1, a2, b1):
        return True
    if abs(d4) <= eps and _on_segment(a1, a2, b2):
        return True
    return False
```

**Про `eps`.** Числа з рухомою комою ніколи не бувають точно нулем. `eps = 1e-9`
означає «вважаємо нулем усе, що менше». Без цього колінеарні випадки
обробляються випадково — залежно від останнього біта мантиси.

```python
# 🟢 src/tcounter/count/geometry.py
def _on_segment(a: Point, b: Point, c: Point) -> bool:
    """True when collinear point c lies within the bounding box of a-b."""
    return (
        min(a[0], b[0]) <= c[0] <= max(a[0], b[0])
        and min(a[1], b[1]) <= c[1] <= max(a[1], b[1])
    )
```

Для **колінеарної** точки перевірки обмежувального прямокутника достатньо:
якщо точка на прямій і в межах прямокутника відрізка — вона на відрізку.

## Напрямок перетину

Знаючи, що перетин є, напрямок читаємо зі зміни знаку:

```python
# 🟢 src/tcounter/count/geometry.py
def crossing(self, prev: Point, curr: Point) -> int:
    """Direction in which the motion prev -> curr crosses this segment."""
    if not segments_intersect(prev, curr, self.p1, self.p2):
        return NO_CROSS
    before = self.signed_side(prev)
    after = self.signed_side(curr)
    if before <= 0.0 < after:
        return TO_POSITIVE
    if before >= 0.0 > after:
        return TO_NEGATIVE
    return NO_CROSS
```

Порядок важливий: **спершу** геометрична перевірка перетину відрізків, **потім**
визначення напрямку. Зворотний порядок дав би ту саму наївну помилку.

## Тест, який це фіксує

```python
# 🟢 tests/test_geometry.py
def test_crossing_line_extension_is_not_a_crossing():
    """The infinite line extends past both endpoints; the gate does not.

    A pedestrian at x = 400 walking across y = 100 flips the sign of
    signed_side but never passes through the counted gate. This is the case
    a bare sign-flip implementation counts and must not.
    """
    assert GATE.crossing((400.0, 50.0), (400.0, 150.0)) == NO_CROSS
    assert GATE.crossing((-50.0, 50.0), (-50.0, 150.0)) == NO_CROSS
```

Де `GATE` — відрізок від (0,100) до (200,100).

## Зони: точка в багатокутнику

Для «товстої зони» замість лінії (запасний варіант для швидких класів, крок 34)
потрібна перевірка «чи точка всередині багатокутника».

**Алгоритм трасування променя** (ray casting): пустити промінь із точки в
нескінченність і порахувати, скільки разів він перетне межу. **Непарна**
кількість — всередині, парна — зовні.

```python
# 🟢 src/tcounter/count/geometry.py
def contains(self, pt: Point) -> bool:
    """Ray-casting point-in-polygon test."""
    x, y = pt
    inside = False
    n = len(self.polygon)
    for i in range(n):
        x1, y1 = self.polygon[i]
        x2, y2 = self.polygon[(i + 1) % n]
        if (y1 > y) != (y2 > y):           # ребро перетинає висоту y?
            x_at_y = x1 + (y - y1) * (x2 - x1) / (y2 - y1)   # де саме
            if x < x_at_y:                 # перетин справа від точки?
                inside = not inside        # перемикаємо
    return inside
```

Умова `(y1 > y) != (y2 > y)` — елегантний спосіб сказати «ребро перетинає
горизонтальну лінію через нашу точку», і одночасно уникнути поділу на нуль для
горизонтальних ребер (для них обидві частини однакові, умова false).

# 19. Машина станів із гістерезисом

Геометрія з розділу 18 відповідає «чи перетнув». Цього все ще не досить, щоб
**порахувати** — бо реальні траєкторії брудні.

## Три проблеми реального світу

**1. Дрижання біля лінії.** Детектор дає рамку з точністю ±3 пікселі. Якщо
людина стоїть рівно на лінії, знак `signed_side` стрибає кожен кадр. Наївний
лічильник видасть серію перетинів замість одного.

```
кадр:  1    2    3    4    5    6
бік:   +    −    +    −    +    −
       ↑    ↑    ↑    ↑    ↑
    порахували 5 перетинів замість 0
```

**2. Розрив і повторне захоплення.** Трек розпався біля лінії, новий ID
з'явився з іншого боку → подвійний підрахунок.

**3. Продовження лінії** — розв'язано в розділі 18.

## Рішення: смуга нечутливості

Навколо лінії вводиться **мертва зона** шириною `± hysteresis_px`
перпендикулярних пікселів. Трек має **стабільний бік**, який оновлюється лише
коли точка-прив'язка **вийшла** зі смуги.

```
                   ┊                     ┊
   бік = −1        ┊   мертва зона       ┊        бік = +1
                   ┊  (бік не змінюється)┊
 ──────────────────┊─────── ЛІНІЯ ───────┊──────────────────
                   ┊                     ┊
              −hysteresis_px        +hysteresis_px
```

Коливання всередині смуги не дають **нічого**. Щоб зарахувати перетин, трек
мусить пройти смугу **наскрізь**.

**Гістерезис** — загальний термін із фізики: система, у якої реакція залежить
не лише від поточного входу, а й від історії. Класичний приклад — термостат:
включається при 18 °C, виключається при 22 °C, а не обидва при 20 °C, щоб не
клацати безперервно.

## Повна машина станів

```
Для кожної пари (трек, лінія) тримаємо:
    stable_side   ∈ {0, −1, +1}     0 = ще не визначено
    stable_point                     точка, де бік визначився
    last_event_frame

На кожному кадрі:
    d = perp_distance(anchor)

    side = +1   якщо d >  hysteresis_px
           −1   якщо d < −hysteresis_px
            0   інакше (у смузі)

    якщо side == 0:
        нічого не робимо                       ← коливання гасяться тут

    якщо stable_side == 0:
        stable_side = side;  stable_point = anchor
        НЕ рахуємо                             ← трек, народжений за лінією
        continue

    якщо side == stable_side:
        stable_point = anchor                  ← освіжаємо точку відліку
        continue

    # бік перевернувся
    direction = line.crossing(stable_point, anchor)   ← перевірка ВІДРІЗКА

    якщо direction ≠ NO_CROSS і дозволено рахувати:
        видати подію

    stable_side = side;  stable_point = anchor         ← фіксуємо завжди
```

## Наш код

```python
# 🟢 src/tcounter/count/counter.py
distance = line.perp_distance(anchor)
if distance > cfg.hysteresis_px:
    side = 1
elif distance < -cfg.hysteresis_px:
    side = -1
else:
    side = 0  # inside the dead band: stable side is unchanged

if side == 0:
    continue

if ls.stable_side == 0:
    # First time this track is unambiguously on one side.
    # Nothing to compare against yet, so no crossing: a track
    # that is born on the far side of the line after a
    # fragmentation cannot double count.
    ls.stable_side = side
    ls.stable_point = anchor
    continue

if side == ls.stable_side:
    # Same side, outside the band: just refresh the reference
    # point so the next crossing test uses a recent position.
    ls.stable_point = anchor
    continue

# The stable side flipped. Confirm the motion really crossed
# the finite segment, not its extension.
direction = NO_CROSS
if ls.stable_point is not None:
    direction = line.crossing(ls.stable_point, anchor)

if direction != NO_CROSS and self._may_count(st, ls, frame_idx):
    ls.last_event_frame = frame_idx
    events.append(Event(...))

# Commit the new side either way, so a track that went round
# the end of the segment is not re-tested on every frame.
ls.stable_side = side
ls.stable_point = anchor
```

Два місця варті окремої уваги.

**`if ls.stable_side == 0: ... continue`** — це захист від проблеми №2.
Трек, що народився **за** лінією (після фрагментації), не має попереднього
боку, тому «перетинати» йому нічого. Ми свідомо обираємо **недорахувати**,
а не перерахувати:

```python
# 🟢 tests/test_counter.py
def test_track_born_on_the_far_side_does_not_count():
    """A fragmented track re-acquired past the gate must not double count.

    The replacement track_id has no established stable side on its first
    unambiguous observation, so there is nothing to cross from. This trades
    a double count for an under count, which is the safer direction for the
    MAPE metric and is why min_track_len can stay low.
    """
    events = walk(vertical(100.0, [120, 140, 160, 180]), track_id=77)
    assert events == []
```

**Останні два рядки — `stable_side = side` навіть коли перетину не було.**
Інакше трек, який обійшов лінію з торця, перевірявся б щокадру нескінченно.

## Три захисні параметри

```python
# 🟢 src/tcounter/count/counter.py
@dataclass
class CounterConfig:
    hysteresis_px: float = 8.0
    min_track_len: int = 3
    debounce_frames: int = 0
    anchor: str = "bottom_center"
    max_track_idle: int = 150
```

### `hysteresis_px`

Напівширина мертвої зони в перпендикулярних пікселях.

Як обрати? З нашої оптики (розділ 24): пішохід на 720p має висоту 137–205
пікселів. 8 пікселів — це ~5 % висоти тіла:

```
  вище за дрижання детектора (±3 px)
  значно нижче за реальний крок людини (~70 cm → десятки пікселів)
```

```python
# 🟢 docstring у CounterConfig
"""
``hysteresis_px`` is in perpendicular pixels at capture resolution.  A
useful anchor for tuning: with f = 8-12 mm at 25 m (plan section 1) a
pedestrian is 137-205 px tall at 720p, so 8 px is roughly 5 % of body
height - above detector jitter, well below a real step.
"""
```

### `min_track_len`

Скільки спостережень трек мусить мати, щоб його перетини рахувались. Захист
від шумових короткоживучих треків.

**Пастка, яка ламає велосипедистів.** Якщо `min_track_len` перевищує бюджет
кадрів на перетин у найшвидшого класу, його перетини **зникають безслідно** —
без помилки, без логу.

```python
# 🟢 docstring
"""
``min_track_len`` must stay below the frames-per-crossing budget of the
*fastest* class being counted, or crossings are silently dropped.  From
the plan's optics table at f = 12 mm: a cyclist gets ~21 frames at
30 FPS but only ~4 at 6 FPS.  Raise this knob only together with a
measured FPS.
"""
```

Є тест на обидва боки:

```python
# 🟢 tests/test_counter.py
def test_min_track_len_suppresses_a_short_track():
    path = vertical(100.0, [40, 60, 80, 120, 140])
    assert len(walk(path, config=CounterConfig(min_track_len=3))) == 1
    # The same trajectory crosses on the 4th observation, so a threshold of
    # 5 drops it. Raising this knob past the frames-per-crossing budget of
    # the fastest class silently loses crossings - see CounterConfig.
    assert walk(path, config=CounterConfig(min_track_len=5)) == []
```

### `debounce_frames`

Кулдаун на пару (трек, лінія). Проти сценарію «людина стоїть на лінії й
хитається з амплітудою **більшою** за мертву зону» — тоді вона законно генерує
чергування +1/−1.

Тонкість: **чиста сума залишається правильною** (події компенсуються), псується
лише сумарна кількість. Тому за замовчуванням кулдаун вимкнений (`0`), і це
параметр для тюнінгу на реальних даних (крок 24).

```python
# 🟢 tests/test_counter.py
def test_debounce_suppresses_loitering_astride_the_gate():
    """Someone standing on the gate, swaying wider than the dead band.

    Without debounce this emits an alternating event per sway. The net count
    stays right either way; debounce keeps the gross count from inflating.
    """
    path = vertical(100.0, [40, 80, 130, 80, 130, 80, 130])
    assert len(walk(path, config=CounterConfig(debounce_frames=0))) > 1
    assert len(walk(path, config=CounterConfig(debounce_frames=100))) == 1
```

І правило перевірки:

```python
# 🟢 src/tcounter/count/counter.py
def _may_count(self, st: _TrackState, ls: _LineState, frame_idx: int) -> bool:
    cfg = self.config
    if st.n_obs < cfg.min_track_len:
        return False
    if cfg.debounce_frames > 0 and ls.last_event_frame is not None:
        if frame_idx - ls.last_event_frame < cfg.debounce_frames:
            return False
    return True
```

# 20. Вибір точки-прив'язки

Трек — це рамка, а перетин лінії визначається для **точки**. Яку точку рамки
брати?

```python
# 🟢 src/tcounter/count/geometry.py
def anchor_point(bbox: Sequence[float], mode: str = "bottom_center") -> Point:
    """Reduce an xyxy bbox to the single point whose trajectory we count."""
    x1, y1, x2, y2 = bbox[:4]
    if mode == "center":
        return ((x1 + x2) / 2.0, (y1 + y2) / 2.0)
    if mode == "bottom_center":
        return ((x1 + x2) / 2.0, y2)
    raise ValueError(f"unknown anchor mode: {mode!r}")
```

## Чому не центроїд

Інтуїтивно хочеться взяти центр рамки. Це помилка для нашої геометрії.

Камера дивиться **під кутом** з висоти на ділянку за 20–30 м. У такій проєкції
вертикаль у кадрі відповідає **глибині** на землі: що нижче в кадрі, то ближче
до камери.

Центроїд людини розташований приблизно на пів висоти тіла **над землею**.
У перспективній проєкції це означає, що він зсунутий у кадрі «вперед» відносно
справжнього положення ніг — і величина зсуву залежить від того, де в кадрі
людина.

Наслідок: людина, що йде **до** камери, перетне лінію за центроїдом **раніше**,
ніж за ногами. Та, що йде **від** камери — **пізніше**. Два напрямки отримують
систематичні зсуви **в різні боки**.

Для нашої головної метрики це найгірший тип помилки: вона не шум, вона
**систематична і різна по напрямках**, тобто розбіжність «туди» і «сюди»
з'явиться навіть на ідеальному детекторі.

## Чому низ-центр

Ноги — точка **контакту з землею**. Вона лежить у площині землі, тому її
проєкція не залежить від висоти об'єкта:

```python
# 🟢 docstring у anchor_point
"""
``bottom_center`` approximates the object's ground contact.  That matters
with the telephoto, oblique view used here: a centroid sits roughly half
a body height above the feet, so a 1.7 m pedestrian would register the
crossing early or late depending on which way they walk, biasing the two
directions against each other.  The feet do not move in depth relative to
the ground plane, so the anchor stays consistent.
"""
```

Бонус: низ рамки стабільніший за верх. Голову детектор часто обрізає або
доповнює залежно від волосся й капюшона; ноги — надійніше.

```python
# 🟢 tests/test_geometry.py
def test_anchor_bottom_center_tracks_the_feet():
    bbox = (100.0, 200.0, 140.0, 340.0)
    assert anchor_point(bbox, "bottom_center") == (120.0, 340.0)
    assert anchor_point(bbox, "center") == (120.0, 270.0)
```

## Коли низ-центр поганий

Для **велосипедиста** точка контакту — колесо, і рамка «велосипедист» включає
і людину, і велосипед, тому низ рамки ≈ точка контакту. Добре.

Для **автомобіля** низ рамки — це нижній край кузова, який теж приблизно в
площині землі. Прийнятно.

Для об'єктів, що не торкаються землі (дрон, птах), `bottom_center` безглуздий —
але таких у нас немає.

# 21. MOTA і чому вона нас обманює

## Означення

**MOTA** (Multiple Object Tracking Accuracy) — із роботи CLEAR MOT,
Bernardin & Stiefelhagen, 2008 ([стаття](https://doi.org/10.1155/2008/246309),
посилання [7] у пропозиції).

Зводить три типи помилок в одне число:

```
╔══════════════════════════════════════════╗
║                FN + FP + IDSW            ║
║   MOTA  =  1 − ─────────────────         ║
║                       GT                 ║
╚══════════════════════════════════════════╝
```

- **FN** — пропущені об'єкти (сума по всіх кадрах)
- **FP** — хибні детекції
- **IDSW** — перемикання ідентичності
- **GT** — загальна кількість екземплярів об'єктів в еталоні (по всіх кадрах!)

**MOTA може бути від'ємною.** Якщо помилок більше, ніж об'єктів — наприклад,
детектор видає купу хибних рамок — чисельник перевищує знаменник. Діапазон
`(−∞, 1]`.

## Числовий приклад і слабке місце

Відео, де в сумі по всіх кадрах 1000 екземплярів пішоходів.

```
Трекер А:  FN = 50,  FP = 30,  IDSW =  5
MOTA_A = 1 − (50 + 30 + 5)/1000 = 1 − 0,085 = 0,915

Трекер Б:  FN = 50,  FP = 30,  IDSW = 10
MOTA_Б = 1 − (50 + 30 + 10)/1000 = 1 − 0,090 = 0,910
```

Трекер Б має **удвічі більше** перемикань ідентичності. MOTA просіла на
**0,5 відсоткових пункту**. Її майже не зрушило.

**Чому.** FN і FP рахуються **по кадрах** і тому бувають тисячами. IDSW
рахуються **по подіях** і бувають десятками. У сумі домінують перші:

```
MOTA ≈ 1 − (детекційні помилки)/GT        ← асоціація майже не впливає
```

## Чому це критично саме для лічильника

Для нас ідентичність — **це все**. Кожне перемикання біля лінії може стати
подвійним підрахунком.

Повернімось до прикладу. Нехай за відео відбулось 100 справжніх перетинів.
5 додаткових IDSW у трекера Б, якщо вони трапились біля лінії, дають
до 5 зайвих підрахунків:

```
похибка підрахунку = 5/100 = 5 %
зміна MOTA         = 0,5 %
```

**Різниця на порядок.** MOTA каже «майже однакові трекери», а наша метрика
каже «один з'їв половину бюджету похибки в 10 %».

Висновок: MOTA потрібна, бо це канонічна метрика й її очікують у звіті. Але
орієнтуватись лише на неї — значить оптимізувати не те.

# 22. HOTA

## Мотивація

**HOTA** (Higher Order Tracking Accuracy) — Luiten et al., IJCV 2021
([стаття](https://arxiv.org/abs/2009.07736), посилання [8] у пропозиції).
Створена **рівно для того**, щоб виправити дисбаланс MOTA.

## Конструкція

HOTA розкладається на дві **рівноправні** половини.

**Детекційна точність:**

```
             |TP|
DetA  =  ──────────────────
          |TP| + |FN| + |FP|
```

Це звичайна метрика «наскільки добре ми знаходимо об'єкти» (вона ж Jaccard
index по детекціях).

**Асоціаційна точність.** Для кожного правильно знайденого об'єкта `c`
дивимось, наскільки добре його **траєкторія** збігається з еталонною:

```
                |TPA(c)|
A(c)  =  ─────────────────────────
          |TPA(c)| + |FNA(c)| + |FPA(c)|
```

де для цього конкретного співставлення:
- **TPA** — скільки інших кадрів теж правильно пов'язані з тим самим ID
- **FNA** — кадри еталонної траєкторії, які наш трек втратив
- **FPA** — кадри нашого треку, які належать іншому еталонному об'єкту

Потім усереднюємо по всіх TP:

```
            1
AssA  =  ─────  ·  Σ  A(c)
          |TP|    c∈TP
```

**Фінальна комбінація — геометричне середнє:**

```
╔══════════════════════════════════════╗
║   HOTA_α  =  √( DetA_α · AssA_α )    ║
╚══════════════════════════════════════╝
```

## Чому геометричне середнє, а не арифметичне

Це сутнісне рішення, не стильове.

```
Арифметичне:  (0,9 + 0,1)/2 = 0,50
Геометричне:  √(0,9 · 0,1)  = 0,30
```

Геометричне середнє **карає за дисбаланс**. Трекер, який ідеально детектує й
нікчемно асоціює, не може «відкупитись» однією половиною. Якщо будь-яка
половина → 0, уся метрика → 0.

Арифметичне середнє дозволило б саме ту підміну, через яку MOTA нас обманює.

## Усереднення по порогах локалізації

`α` — поріг IoU, за яким детекція вважається співставленою. HOTA усереднюється
по `α` від 0,05 до 0,95 із кроком 0,05 (19 значень):

```
HOTA = (1/19) · Σ_α HOTA_α
```

Це додає третю складову — **точність локалізації**, якої немає ні в MOTA, ні в
IDF1. Трекер, що дає правильні ідентичності в приблизно правильних місцях,
отримає менше, ніж той, що дає їх точно.

## Яку цифру дивимо ми

**AssA.** Бо похибка лічильника народжується з розривів ідентичності, а не з
промахів детекції.

Практичне правило для нашого звіту:

```
DetA низька, AssA висока  →  проблема в детекторі: модель, вхід, пороги
DetA висока, AssA низька  →  проблема в асоціації: FPS, гіперпараметри трекера
обидві низькі             →  проблема в даних або геометрії камери
```

Це і є те, що пропозиція має на увазі словами «збалансовано враховує якість
детекції та асоціації».

## Де взяти

**Не реалізовувати самостійно.** Канонічна реалізація —
[TrackEval](https://github.com/JonathonLuiten/TrackEval) від автора статті.
Крок 45 плану саме про це.

# 23. Наші метрики: MAPE, WAPE, bias

## Чому потрібна третя метрика

MOTA і HOTA міряють **якість трекінгу**. Місту якість трекінгу не потрібна.
Місту потрібно: «скільки людей пройшло між 14:00 і 14:15».

Пропозиція це розуміє й визначає головну метрику саме так: відносна похибка
підрахунку за 15-хвилинними інтервалами, окремо по класу й напрямку.

MOTA і HOTA залишаються **діагностикою**, яка пояснює, *чому* головна метрика
така, а не інакша.

## MAPE

**MAPE** (Mean Absolute Percentage Error, середня абсолютна відсоткова похибка):

```
╔═══════════════════════════════════════╗
║            1       |ŷᵢ − yᵢ|          ║
║  MAPE  =  ───  Σ  ──────────          ║
║            n   ᵢ      yᵢ              ║
╚═══════════════════════════════════════╝
```

де `yᵢ` — ручний підрахунок у бакеті `i`, `ŷᵢ` — наш, `n` — кількість бакетів.

**Бакет** (bucket) — часовий інтервал, у який групуються події. У нас 15 хвилин =
900 секунд. Групування робиться цілочисельним діленням:

```python
# 🟢 eval/count_mape.py
key = BucketKey(
    bucket_start=int(event.ts_utc // bucket_seconds) * bucket_seconds,
    line_id=event.line_id,
    class_id=event.class_id,
    direction=event.direction,
)
```

`//` — цілочисельне ділення. `ts // 900 * 900` «притискає» будь-який час до
початку його 15-хвилинного інтервалу.

Ключ бакета — **чотиривимірний**: час, лінія, клас, напрямок. Бо пропозиція
вимагає розбивку по класу й напрямку окремо.

## Проблема MAPE на малих числах

MAPE ділить на **власну** кількість у кожному бакеті. На тихій алеї
15-хвилинний бакет містить 3–5 людей. Один промах там — це 20–33 % похибки, і
середнє по бакетах починає визначатись найпорожнішим бакетом.

Конкретно (це справжній вихід нашого e2e-прогону):

```
бакет 1:  еталон 13, ми 12   →  APE = 1/13  = 7,69 %
бакет 2:  еталон 10, ми  9   →  APE = 1/10  = 10,00 %
бакет 3:  еталон  4, ми  3   →  APE = 1/4   = 25,00 %

MAPE = (7,69 + 10,00 + 25,00)/3 = 14,23 %
```

Три промахи з 27 людей — а MAPE показує 14,23 %, бо третій бакет маленький.

## WAPE

**WAPE** (Weighted Absolute Percentage Error) — ділить на **суму**, не на
кожне окремо:

```
╔═══════════════════════════════════╗
║           Σᵢ |ŷᵢ − yᵢ|            ║
║  WAPE  =  ────────────            ║
║             Σᵢ yᵢ                 ║
╚═══════════════════════════════════╝
```

Той самий приклад:

```
WAPE = (1 + 1 + 1)/(13 + 10 + 4) = 3/27 = 11,11 %
```

**Різниця в тому, що зважується.** MAPE зважує кожен **бакет** однаково. WAPE
зважує кожну **людину** однаково. Для фізичної величини «скільько людей
пройшло» друге природніше й значно стабільніше.

MAPE залишається заявленою метрикою, бо пропозиція на неї зобов'язалась.
WAPE — те, за чим тюнити.

## Bias

Обидві попередні беруть модуль і тому не кажуть **у який бік** ми помиляємось.
А це діагностично найцінніше:

```
╔═══════════════════════════════════╗
║           Σᵢ (ŷᵢ − yᵢ)            ║
║  bias  =  ────────────            ║
║             Σᵢ yᵢ                 ║
╚═══════════════════════════════════╝
```

```
bias = −3/27 = −11,11 %     ← недораховуємо
```

| Знак | Інтерпретація | Де шукати причину |
|---|---|---|
| **bias < 0** | недораховуємо | пропуски детектора, завеликий `min_track_len`, завелика мертва зона |
| **bias > 0** | перераховуємо | фрагментація треків, замала мертва зона, подвійні спрацювання |
| **bias ≈ 0, MAPE велика** | помилки компенсуються | шум, а не систематичний зсув |

Останній рядок важливий: нульовий bias при великій MAPE означає, що ми
помиляємось в обидва боки випадково — це зовсім інша проблема, ніж
систематичний зсув, і лікується інакше.

## Порожні бакети

MAPE **не визначена**, коли `yᵢ = 0` — ділення на нуль. Такі бакети не можуть
увійти в середнє.

Але просто їх викинути було б нечесно: **хибні спрацювання найімовірніші саме
в тихі періоди**, і викидання сховало б їх. Тому вони звітуються окремо:

```python
# 🟢 eval/count_mape.py
if gt == 0:
    # MAPE cannot score this bucket; surface it instead of hiding it.
    report.empty_buckets += 1
    report.false_positives_in_empty_buckets += pred
    continue
```

І є тест, який фіксує, що відсутність MAPE не читається як успіх:

```python
# 🟢 tests/test_count_mape.py (видалено при спрощенні, повертається з кроком 17)
def test_false_positives_in_empty_buckets_are_reported_not_dropped():
    """MAPE cannot score a zero-truth bucket; the error must still surface."""
    report = compare({BucketKey(BASE, "gate", 0, 1): 4}, {})
    assert report.overall.buckets_scored == 0
    assert report.empty_buckets == 1
    assert report.false_positives_in_empty_buckets == 4
    # No scored bucket means no MAPE, which must not read as success.
    assert report.overall.mape is None
    assert not report.meets_target()
```

## Повний вихід

```
counting error vs manual ground truth
  buckets scored : 3  (+0 empty, excluded from MAPE)
  ground truth   : 27
  predicted      : 24
  MAPE           :  14.23 %   <- headline metric

```

Зверніть увагу: `class 1` (велосипедисти) має 25 % при еталоні 4. Саме це
й ілюструє, чому розбивка по класах обов'язкова — у загальній цифрі
велосипедисти загубились би серед пішоходів.

# 24. Оптика камери

Розділ, який перетворює «наведемо камеру на алею» в числа.

## Фокусна відстань і поле зору

**Фокусна відстань** `f` (мм) — характеристика об'єктива. Чим більша, тим
вужчий кут і більше «зум».

**Сенсор** має фізичні розміри. Наш IMX323 має формат 1/2.9″, що відповідає
активній зоні приблизно **5,08 × 2,86 мм**.

> Формати сенсорів («1/2.9 дюйма») — історичний спадок від телевізійних
> трубок і **не** відповідають жодному реальному розміру. Треба дивитись
> специфікацію.

**Поле зору** (FOV, field of view). З простої тригонометрії: сенсор на
відстані `f` від оптичного центру, половина сенсора `W/2` утворює кут:

```
            W_сенсора
HFOV = 2 · arctan( ───────── )
             2 · f
```

## Покриття на відстані

Скільки метрів по ширині потрапляє в кадр на відстані `D`:

```
W = 2 · D · tan(HFOV/2)
```

Але `tan(HFOV/2) = W_сенсора/(2f)`, отже:

```
╔═══════════════════════════╗
║          W_сенсора        ║
║   W = D · ─────────       ║
║              f            ║
╚═══════════════════════════╝
```

Це **подібні трикутники** — та сама формула, що для тіні від предмета.
Аналогічно по вертикалі з `H_сенсора`.

## Наша таблиця, виведена

Для `D = 25 м`, сенсор 5,08 × 2,86 мм:

```
f = 12 мм:
  W = 25 · 5,08/12 = 10,58 м
  H = 25 · 2,86/12 =  5,96 м
  HFOV = 2·arctan(5,08/24) = 2·11,96° = 23,9°
```

Висота пішохода (1,7 м) у пікселях при висоті кадру 480:

```
              1,7 м
піксели = ───────── · 480 = 0,2852 · 480 = 137 px
            5,96 м
```

Повна таблиця:

| f, мм | HFOV | W @25м | H @25м | пішохід @480p | @720p |
|---|---|---|---|---|---|
| 2,8 | 84,4° | 45,4 м | 25,5 м | 32 px | 48 px |
| 6,0 | 45,9° | 21,2 м | 11,9 м | 68 px | 103 px |
| **8,0** | **35,2°** | **15,9 м** | **8,9 м** | **91 px** | **137 px** |
| **12,0** | **23,9°** | **10,6 м** | **6,0 м** | **137 px** | **205 px** |

## Метрів на піксель

Величина, яка знадобилась у розділі 16:

```
        H @D        5,96
k  =  ────────  =  ─────  =  0,0124 м/px  =  12,4 мм/px
       висота       480
```

Тобто на повному зумі один піксель — це 1,24 см на землі. Ширина плечей
0,55 м → 0,55/0,0124 ≈ **44 пікселі**. (Бокс вужчий, ~33 px, бо проєкція
плечей під кутом.)

## Чому обрано 8–12 мм

Три вимоги, що сходяться:

1. **Покриття має відповідати ширині алеї.** 10–16 м — рівно алея з
   узбіччями. На широкому куті (2,8 мм) у кадр попадає 45 м — купа зайвого,
   де нічого не рахується, але все обробляється.
2. **Об'єкт має бути достатньо великим для nano-детектора.** 137–205 пікселів
   висоти — із запасом. При вході мережі 320 це дає 60–90 пікселів, що для
   YOLO-nano комфортно. На 2,8 мм пішохід має 32 пікселі — на межі.
3. **Час у кадрі має давати достатньо кадрів.** 7,6 с для пішохода, 2,1 с для
   велосипедиста. При 30 FPS це 228 і 63 кадри — з величезним запасом для
   асоціації.

## Час у кадрі й бюджет кадрів

```
час = W / v
```

| f, мм | W | пішохід (1,4 м/с) | велосипедист (5 м/с) |
|---|---|---|---|
| 8 | 15,9 м | 11,3 с | 3,2 с |
| 12 | 10,6 м | 7,6 с | 2,1 с |

Помножте на FPS — отримаєте кадри:

| f=12 мм | FPS=2 | FPS=6 | FPS=30 |
|---|---|---|---|
| пішохід | 15 | 45 | 228 |
| велосипедист | 4 | 13 | 63 |
| автомобіль (14 м/с) | 1,5 | 4,5 | 23 |

**Рядок «велосипедист, FPS=2: 4 кадри»** — це і є той випадок, де трек фізично
не встигає ініціалізуватись (розділ 11), не кажучи про асоціацію.

## Конфіг

```yaml
# 🟢 configs/site_ucu_alley.yaml
camera:
  model: ELP-USBFHD06H-MFV
  sensor: IMX323
  # Set during W1 characterisation and then locked with a ring clamp.
  focal_length_mm: 10.0
  distance_m: 25.0
  reference_frame: data/calib/ucu_alley_reference.jpg
```

**«Locked with a ring clamp»** — не педантизм. Варіфокальний об'єктив має
кільця зуму й фокуса, які повертаються від вібрації. Якщо зум змінився,
`f` інший, покриття інше, **а геометрія лінії в конфізі посилається на старий
кадр**. Лічильник працюватиме й даватиме неправильні числа.

Тому: фіксатор на кільцях + референсний кадр у конфізі для перевірки.

Геометрія лінії зберігається в [0, 1] від розміру кадру:

```yaml

  - id: alley_gate
    p1: [0.08, 0.62]
    p2: [0.92, 0.58]
```

вимагала б перекалібрування — і хтось би забув.

# 25. Edge: FLOPs, квантизація, пам'ять

## FLOPs і як вони масштабуються

**FLOP** = Floating Point Operation, одна операція з рухомою комою.
**GFLOPs** = мільярд таких операцій. Це міра «скільки роботи» в одному проході
мережі.

YOLOv8n при вході 640 — 8,7 GFLOPs.

**Масштабування з розміром входу.** Вартість згортки пропорційна площі карти
ознак, а площа — квадрату лінійного розміру:

```
                           ( новий розмір )²
FLOPs(новий) = FLOPs(640) · (─────────────)
                           (     640      )
```

```
при 320: 8,7 · (320/640)² = 8,7 · 0,25 = 2,18 GFLOPs
при 416: 8,7 · (416/640)² = 8,7 · 0,42 = 3,67 GFLOPs
при 256: 8,7 · (256/640)² = 8,7 · 0,16 = 1,39 GFLOPs
```

**Зменшення входу вдвічі дає вчетверо менше обчислень.** Це найдешевший важіль
прискорення — і найперший, за який варто братись.

## Чому FLOPs не вся правда

Реальна швидкість залежить не лише від обчислень, а й від **пропускної
здатності пам'яті**: ваги й карти ознак треба читати з RAM.

Груба оцінка «арифметичної інтенсивності»:

```
інтенсивність = FLOPs / байти, прочитані з пам'яті
```

Якщо інтенсивність низька, процесор простоює в очікуванні пам'яті —
обчислювальна потужність не має значення. Це називають **memory-bound**.

Практичний наслідок для нас: Pi 5 має LPDDR4X-4267, Pine A64 — DDR3. Різниця
в пропускній здатності в кілька разів **додається** до різниці в ядрах.
Тому реальний розрив між платами (6–8×) більший, ніж можна порахувати лише
за тактовою частотою (2,09×).

## Чому Cortex-A76 настілько швидший за A53

| | Cortex-A53 (Pine A64) | Cortex-A76 (Pi 5) |
|---|---|---|
| Частота | 1,15 ГГц | 2,4 ГГц |
| Виконання | **in-order**, 2-wide | **out-of-order**, 4-wide |
| Пам'ять | DDR3 | LPDDR4X-4267 |

**In-order** означає: якщо інструкція чекає на дані з пам'яті, уся черга
стоїть. **Out-of-order** дозволяє процесору виконувати наступні незалежні
інструкції, поки одна чекає — це дає велику частину виграшу IPC.

**IPC** (Instructions Per Cycle) — скільки інструкцій виконується за такт.
A76 має приблизно втричі вищий IPC за A53 на таких навантаженнях.

Разом: `2,09 (частота) × ~3 (IPC) ≈ 6×`, плюс пам'ять → **6–8×** загалом.
Це збігається з виміряними бенчмарками.

## Чому Mali-400MP2 не допомагає

На Pine A64 є GPU, і логічно було б використати її. Не вийде:
**Mali-400MP2 підтримує лише OpenGL ES 2.0** — графічний API без обчислювальних
шейдерів. Немає ні OpenCL, ні Vulkan compute, ні CUDA.

Тобто GPU може малювати трикутники, але не може виконати згортку. Для
машинного навчання вона непридатна.

```python
# 🔵 довідкова реалізація
self._net.opt.use_vulkan_compute = False  # Mali-400 has no OpenCL/Vulkan compute
self._net.opt.num_threads = num_threads   # ← усе на 4 ядра CPU
```

## Квантизація

**Квантизація** — зберігати й обчислювати числа в меншій точності.

| Тип | Біт | Діапазон | Застосування |
|---|---|---|---|
| fp32 | 32 | ±3,4·10³⁸ | навчання, звичайний інференс |
| fp16 | 16 | ±65 504 | інференс на GPU |
| **int8** | **8** | **−128…127** | **інференс на CPU/NPU** |

### Афінна квантизація

Відображення між реальним числом `r` і цілим `q`:

```
╔════════════════════════╗
║   r  =  S · (q − Z)    ║
╚════════════════════════╝
```

- `S` — **масштаб** (scale), число з рухомою комою
- `Z` — **нульова точка** (zero point), ціле

Обчислення `S` і `Z` з діапазону `[r_min, r_max]`:

```
      r_max − r_min       r_max − r_min
S  =  ─────────────  =  ───────────────
      q_max − q_min            255

Z  =  round( q_min − r_min / S )
```

**Симетрична** квантизація (типова для ваг) бере `Z = 0`:

```
S = max|r| / 127
```

### Приклад

Тензор ваг у діапазоні `[−0,8; 1,2]`. Асиметрично, int8 (`q ∈ [−128, 127]`):

```
S = (1,2 − (−0,8))/255 = 2,0/255 = 0,00784
Z = round(−128 − (−0,8)/0,00784) = round(−128 + 102) = −26

Перевірка: q = 127  →  r = 0,00784·(127 − (−26)) = 0,00784·153 = 1,200 ✓
           q = −128 →  r = 0,00784·(−128 + 26)  = 0,00784·(−102) = −0,800 ✓
```

### Калібрування

`S` і `Z` залежать від реального діапазону значень, який **для активацій**
(не ваг) відомий лише під час роботи. Тому перед квантизацією ганяють
**калібрувальний набір** — кілька сотень репрезентативних зображень — і
збирають статистику min/max або перцентилі по кожному тензору.

**Критично:** калібрувальний набір мусить бути з **нашого** розподілу. Якщо
калібрувати на COCO, а працювати на алеї при сутінках, діапазони будуть не ті,
і точність просяде більше, ніж треба.

Тому в плані (крок 46) стоїть:

```
Переконатись, що int8-пороги перекалібровані — fp32-ві не переносяться.
```

### Чому `conf_threshold` «з'їжджає»

Квантизація вносить шум в оцінки класів. Розподіл впевненостей трохи
зсувається й розмивається. Поріг 0,35, підібраний на fp32, після квантизації
відрізає інакше — зазвичай агресивніше.

Це не баг, а наслідок. Тому поріг — частина калібрування, а не константа.

### Чому int8 швидший

Дві причини, і друга важливіша:

1. **Вчетверо менше трафіку пам'яті.** Ваги й активації займають 1 байт
   замість 4. На memory-bound навантаженні це прямий виграш.
2. **SIMD-інструкції.** ARM NEON має інструкції (`SDOT`, `SMLAL`), які за один
   такт виконують 4–8 int8 множень-додавань, тоді як для fp32 — лише 4
   операції на 128-бітному регістрі.

**SIMD** = Single Instruction, Multiple Data — одна інструкція обробляє кілька
чисел одночасно. **NEON** — реалізація SIMD в ARM.

Разом це дає ~1,5–2× на практиці.

## Чому ми обійшлись без квантизації

Виміряні бенчмарки для YOLOv8n на Pi 5:

```
NCNN fp32 @640         ~12 FPS
NCNN fp32 @320         ~30-40 FPS   ← достатньо навіть для велосипедиста (13,6)
NCNN int8 @320         ~30-40 FPS   ← те саме
```

Оскільки fp32 @320 уже проходить із запасом ×2,5, квантизація прибрана з
критичного шляху. Це видалило цілий воркстрім: калібрувальний набір,
`ncnn2table`, перекалібрування порогів, ризик просідання mAP.

int8 залишається лише для ablation на Pine A64 (крок 46), де він **обов'язковий**.

## Тротлінг

**Термічний тротлінг** — процесор знижує частоту, щоб не перегрітись.
Виявляється **лише на довгих прогонах**: перші 30 секунд працюють на повній
частоті, а за 5 хвилин у закритому корпусі швидкість може просісти на
десятки відсотків.

Тому в бенчмарку окремо міряються перша й остання десята частина прогону:

```python
# 🔵 довідкова реалізація, повертається на кроці 28
# The first and last tenth separate a cold number from a sustained one.
tenth = max(1, len(latencies_ms) // 10)
result = {
    "fps_first_tenth": round(tenth / (sum(latencies[:tenth]) or 1e-9), 2),
    "fps_last_tenth":  round(tenth / (sum(latencies[-tenth:]) or 1e-9), 2),
    ...
}
drop = 1.0 - result["fps_last_tenth"] / max(result["fps_first_tenth"], 1e-9)
if drop > 0.10:
    print(
        f"\nWARNING: throughput fell {drop * 100:.0f} % over the run. "
        "Treat fps_last_tenth as the deployable number, and check cooling."
    )
```

**`fps_last_tenth` — це число, яке можна обіцяти.** `fps_first_tenth` — число
для маркетингу.

## COCO

**COCO** (Common Objects in Context) — Lin et al., ECCV 2014

~330 тис. зображень, 80 класів, рамки + сегментаційні маски. Стандартний набір

Критично для нас: потрібні класи **вже є в COCO**:

```yaml

    0: person
    1: bicycle
    2: car

    5: bus
    7: truck
```

(ID не послідовні, бо це оригінальна нумерація COCO з пропусками.)

Саме тому пропозиція каже «ми не тренуємо детектор з нуля», а крок 17 плану

## Формат MOT

MOT-набори зберігають анотації в простому CSV:

```
frame, id, bb_left, bb_top, bb_width, bb_height, conf, x, y, z
1, 1, 912.0, 484.0, 97.0, 109.0, 1, -1, -1, -1
1, 2, 1338.0, 418.0, 167.0, 379.0, 1, -1, -1, -1
2, 1, 912.0, 484.0, 97.0, 109.0, 1, -1, -1, -1
```

Поля: номер кадру, **стійкий ID об'єкта**, рамка у формі `xywh`, впевненість,
три координати 3D (−1 для 2D-наборів).

Друга колонка — те, чого немає в COCO й що робить MOT придатним для
оцінювання трекінгу.

## MOT17 vs MOT20 — чому для нас MOT20

**MOT Challenge** — Milan et al., 2016
([стаття](https://arxiv.org/abs/1603.00831), посилання [10] у пропозиції).

| | MOT17 | MOT20 |
|---|---|---|
| Камера | **мішана: частина послідовностей рухома** | нерухома |
| Точка зору | переважно близька дистанція, рівень очей | **піднята** |
| Щільність | помірна | дуже висока (натовпи) |
| Послідовностей | 7 train + 7 test | 4 train + 4 test |

**MOT20 нам геометрично ближчий:** нерухома камера з піднятої точки — це наша
конфігурація. На рухомій камері віртуальна лінія підрахунку не має сенсу
взагалі, бо вона прив'язана до кадру, а кадр рухається.

**Ліцензія CC BY-NC-SA 4.0** — некомерційна, share-alike. Тому пропозиція
займає чітку позицію: **інференс так, донавчання ні**, щоб не успадкувати
обмеження у вагах моделі.

## Безкоштовний ground truth для перетинів

Жоден публічний набір із пішоходами не дає еталонних **перетинів лінії** — лише
рамки й ID. Але це обходиться.

MOT-анотації містять покадрові рамки **плюс стійкі ID**. Якщо подати ці
GT-треки прямо в наш `LineCounter`, минаючи детектор і трекер, отримаємо
підрахунок, який дав би **ідеальний** детектор+трекер.

Це дає декомпозицію, яку інакше не отримати:

| Порівняння | Що ізолює |
|---|---|
| `count(GT-треки)` vs людина | помилку **самої логіки підрахунку** |
| `count(YOLO+ByteTrack)` vs `count(GT-треки)` | внесок **детекції й трекінгу** |

Тобто можна прогнати весь метричний апарат на реальному людському руху ще до
того, як з'явиться перший власний кадр.

## Спліти

**Train / validation / test** — три незалежні частини даних:

- **train** — на чому модель навчається
- **validation** (val) — на чому підбираються гіперпараметри
- **test** — на чому міряється фінальний результат, **один раз**

**Витік даних** (data leakage) — коли інформація з test просочується в train.
Найпідліша форма для відео: **сусідні кадри майже ідентичні**. Якщо нарізати
кадри випадково й поділити, кадр 1001 попаде в train, а 1002 — у test, і
модель покаже чудову точність, яка не має жодного стосунку до реальності.

**Правило для відео: ділити по сесіях або кліпах, ніколи по кадрах.**

| **MAPE** | Mean Absolute Percentage Error; наша заявлена головна метрика |
| **memory-bound** | навантаження, обмежене пропускною здатністю пам'яті, не обчисленнями |
| **MJPEG** | кодек, де кожен кадр — окремий JPEG; простий, але об'ємний |
| **MOT** | Multiple Object Tracking; також назва сімейства бенчмарків |
| **MOTA** | Multiple Object Tracking Accuracy; домінується помилками детекції |
| **NEON** | SIMD-розширення ARM |
| **NMS** | Non-Maximum Suppression, прибирання дублікатних рамок |
| **occlusion** | перекриття одного об'єкта іншим |
| **precision** | `TP/(TP+FP)` — частка правильних серед знайдених |
| **quantization** | зниження точності чисел для швидкості й економії пам'яті |
| **recall** | `TP/(TP+FN)` — частка знайдених серед наявних |
| **re-ID** | re-identification, упізнавання того самого об'єкта після перерви |
| **SIMD** | Single Instruction Multiple Data — одна інструкція на кілька чисел |
| **SORT** | Simple Online and Realtime Tracking; Калман + IoU + угорський алгоритм |
| **стратифікація** | побудова вибірки так, щоб усі важливі режими були представлені |
| **тензор** | багатовимірний масив чисел |
| **throttling** | зниження частоти процесора через перегрів |
| **TP** | true positive, вірне спрацювання |
| **track ID** | стійкий ідентифікатор об'єкта між кадрами |
| **UVC** | USB Video Class — стандарт, завдяки якому камера працює без драйверів |
| **WAL** | Write-Ahead Logging, режим SQLite, стійкіший до обриву живлення |
| **WAPE** | Weighted APE: `Σ|ŷ−y|/Σy`; стабільніша за MAPE на малих числах |
| **YOLO** | You Only Look Once; сімейство одноетапних детекторів |
| **згортка** | операція ковзного віконця, що виділяє локальні ознаки |
| **угорський алгоритм** | оптимальний розв'язок задачі про призначення за O(n³) |

# Що тут наше

Підсумок, важливий для фінального звіту. Пропозиція це визнає прямо:
**«Наш внесок — не нова архітектура, а адаптація».** Конкретно:

| Розділ | Звідки |
|---|---|
| 1–15, 21–22, 26 | готові цеглини з літератури |
| **16** | **наше: виведення `f_min` і доведення інваріантності до масштабу** |
| **18–20** | **наше: шар підрахунку з перетинів — цього немає в жодній статті** |
| **23** | **наше: WAPE поруч із MAPE, явне звітування порожніх бакетів** |
| 24–25 | інженерна адаптація під конкретне залізо й оптику |

Розділ 16 — це причина, чому проєкт не є «склеюванням туторіалів»: усі
туторіали знімають на 30 FPS і цієї проблеми не бачать. Вона з'являється
рівно тоді, коли починаєш робити це на дешевому заліза в реальних умовах —
тобто рівно там, де лежить наукова цінність.
